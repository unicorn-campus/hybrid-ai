## 3. ACI 설계 원칙 여섯 가지

- 패턴: `cards`
- 리드문: 도구는 모델을 위한 사용자 인터페이스다
- 1. **설명 문서** - 신입 개발자용 문서처럼 작성 / - 무엇을, 언제 쓰나와 쓰지 않나 / - 파라미터 예시와 반환 형태
- 2. **적은 도구** - 워크플로 단위, list_all 대신 search / - 기능이 겹치지 않게 자기완결적으로 / - 정의 토큰은 매 요청 포함, count_tokens로 측정 / - 정의가 바뀌면 프롬프트 캐시 무효화
- 3. **이름 짓기** - 서비스_리소스_동작 형태 / - id 대신 ticket_id / - 반환은 사람이 읽는 필드로
- 4. **응답 크기** - 전체 목록 대신 페이지네이션 / - response_format으로 상세도 선택 / - 기본 응답이 실행기 상한보다 작게 / - 자세한 설계는 다음 슬라이드
- 5. **에러 메시지** - 무엇이 틀렸는지 / - 어떻게 고치는지 / - 못 고치면 무엇을 할지
- 6. **poka-yoke** - 애초에 틀릴 수 없게 만들기 / - 예: 절대경로만 받는 도구 / - 예: closed를 enum에서 제외
- 핵심 메시지: 사람도 헷갈리는 도구 선택은 에이전트도 헷갈린다
- 출처: 출처: Anthropic Engineering, "Writing effective tools for agents" (2025-09-11), "Effective context engineering for AI agents" (2025-09-29)

## 4. 토큰 효율적인 응답 설계

- 패턴: `table`
- 리드문: 도구의 기본 응답 자체를 실행기 상한보다 작게 만든다

표: 응답 크기를 다루는 장치

| 장치 | 구현 | 효과 |
|---|---|---|
| response_format | concise 또는 detailed | 필요한 상세도를 모델이 고름 |
| 대상 지정 조회 | doc_ids 최대 2개 | 훑기 후 골라 읽기 지원 |
| 페이지네이션 | page, page_size, has_more | 필요한 만큼만 더 가져옴 |
| 잘라내기 기본값 | detailed 2건, 발췌 약 2,400B | 기본 응답이 상한보다 작음 |
| 출력 크기 상한 | 실행기 max_bytes 4KB | 구현 실수를 막는 최후 방어선 |

- 보조 설명: 잘라내기 기본값과 출력 크기 상한은 역할이 다름; 정상 호출된 도구는 실행기 상한에 걸리지 않아야 함; 상한에 걸렸다면 도구 설계가 잘못된 것으로 봄

<!-- 노트: 사람은 목록을 눈으로 훑지만 모델에게 목록 전체는 컨텍스트에 쌓이는 토큰입니다. concise로 훑고 인용할 문서만 doc_ids로 골라 detailed로 읽는 순서를 도구가 직접 지원합니다. 실행기의 4KB 상한은 3.6에서 구현하는 마지막 안전망입니다. -->

## 7. poka-yoke를 입력 모델로 구현

- 패턴: `code`
- 리드문: 잘못된 행동은 스키마와 검증기로 표현할 수 없게 한다

```python
class TicketUpdateInput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    ticket_id: TicketId          # TCK-000123으로 정규화
    comment: str = Field(min_length=5, max_length=2000)
    # closed는 enum에 없음: 종료는 사람만 한다
    new_status: Literal["pending", "resolved"] | None = None
    resolution_note: str | None = None

    @model_validator(mode="after")
    def resolved_needs_note(self):
        if (self.new_status == "resolved"
                and not self.resolution_note):
            raise ValueError("resolution_note가 필요합니다...")
        return self
```

- 보조 설명: TicketId는 AfterValidator로 대소문자를 정규화하고 숫자만 오면 올바른 형식을 안내; **extra="forbid"**로 모르는 필드를 거부; 필드 사이 규칙은 model_validator가 검사; ticket_lookup은 ticket_id 또는 requester_email이 없으면 거부
- 출처: 출처: 교재 harness/tools/models.py 발췌(Field 설명 생략)

## 8. @beta_tool로 빠르게 정의하기

- 패턴: `code`
- 리드문: 타입 힌트와 docstring에서 입력 스키마를 만든다

```python
@beta_tool
def docs_search(query: str | None = None,
                doc_ids: list[str] | None = None,
                page: int = 1) -> str:
    """사내 문서를 검색하거나 지정 문서를 자세히 읽습니다.
    티켓 상태 확인에는 ticket_lookup을 쓰세요.
    """
    try:  # 스키마와 별개로 pydantic 재검증
        args = DocsSearchInput(query=query, doc_ids=doc_ids,
                               page=page)
    except ValidationError as e:
        raise ToolError(_validation_message(e)) from e
    return impl.docs_search(args)
```

- 보조 설명: client.beta.messages.tool_runner가 2장의 루프를 대신 돌림; 프로토타입에는 가장 빠른 방법; 타임아웃, 출력 상한, 감사 로그를 함수마다 반복해야 함; ToolError가 is_error로 바뀌는지는 ANTHROPIC_LOG=debug로 SDK 버전별 확인
- 출처: 출처: 교재 beta_tool_demo.py 발췌(response_format 인자와 Args 설명 생략)

<!-- 노트: 예외를 던졌을 때 tool_runner의 처리는 SDK 버전마다 다를 수 있습니다. is_error가 붙는 경우, 문자열로만 바뀌는 경우, 예외가 루프 밖으로 터지는 경우 중 어느 것인지 확인 스크립트로 기록해 두면 SDK를 올릴 때 회귀 확인 기준이 됩니다. @beta_tool 데코레이터 자체의 strict 옵션은 집필 시점 문서에서 확인하지 못했습니다. 그래서 to_dict() 결과에 strictify와 strict: true를 덧붙여 messages.create로 직접 보내고 execute_tool로 실행합니다. -->

## 9. strict와 pydantic 재검증

- 패턴: `two_column`
- 리드문: strict는 스키마에 맞는 JSON까지만 보장한다
- left [strict]: 도구 입력이 스키마에 맞는 유효한 JSON임을 보장; 객체마다 additionalProperties: false 지정; minimum/maximum, minLength/maxLength, minItems/maxItems 미지원; strictify가 미지원 키워드와 기본값을 설명문으로 옮기고 title은 삭제; 지원하지 않는 모델에 strict를 보내면 400 오류; 지원 모델, 도구 수 제한, 베타 헤더는 적용 전 structured outputs 문서로 확인
- right [재검증]: 길이와 범위 제약은 pydantic이 실제로 검사; resolved면 resolution_note 필수 같은 필드 간 규칙; 티켓 번호 정규화처럼 스키마로 못 쓰는 처리; strict가 꺼진 경로(다른 SDK, 테스트)의 입력
- 핵심 메시지: 입력 검증의 최종 책임은 하네스 코드가 진다
- 출처: 출처: Anthropic, Structured outputs (Claude Platform Docs)

<!-- 노트: schema.py의 strictify는 지원하지 않는 키워드와 기본값을 설명문으로 옮기고 title을 지우며 객체마다 additionalProperties: false를 넣습니다. 설명문으로 옮겨진 길이와 범위 제약은 모델에게 안내만 될 뿐이므로, 실제 검사는 오른쪽의 pydantic 재검증이 맡습니다. 지원 범위는 문서 버전에 따라 바뀌므로, 적용 전에 문서를 확인하지 않으면 400 오류로 요청 자체가 실패할 수 있습니다. -->

## 10. 두 정의 경로: @beta_tool vs ToolSpec

- 패턴: `table`
- 리드문: 프로토타입은 @beta_tool, 운영 하네스는 ToolSpec 레지스트리로

표: 도구 정의 경로 비교

| 구분 | @beta_tool(프로토타입) | ToolSpec.to_api()(운영) |
|---|---|---|
| 스키마 출처 | 타입 힌트와 docstring | pydantic input_model |
| strict 적용 | 옵션 미확인 → to_dict()에 strictify와 strict 덧붙여 직접 전송 | strictify 후 strict: true |
| 범위와 교차 검증 | 함수 안에서 pydantic 재검증 | 실행기가 input_model로 검증 |
| 루프 | tool_runner(strict 덧붙이면 직접 루프) | 2장 루프에서 실행기 호출 |

## 11. Agent SDK 도구 서버 만들기

- 패턴: `code`
- 리드문: @tool 핸들러가 공통 실행기를 호출해 검증, 타임아웃, 감사 로그를 공유

```python
def as_sdk_tool(spec: ToolSpec, ctx: RunContext):
    @tool(spec.name, spec.description,
          to_strict_schema(spec.input_model),
          annotations=ToolAnnotations(
              readOnlyHint=spec.read_only))
    async def handler(args: dict) -> dict:
        call_id = f"sdk_{uuid.uuid4().hex[:8]}"
        r = await execute_tool(spec.name, call_id, args,
                               REGISTRY, ctx)
        out = {"content": [{"type": "text",
                            "text": r["content"]}]}
        if r.get("is_error"): out["is_error"] = True
        return out
    return handler
```

- 보조 설명: create_sdk_mcp_server로 **인프로세스 MCP 서버** 생성; 도구 이름은 mcp__<서버>__<도구> 규칙(예: mcp__helpdesk__docs_search); **readOnlyHint**는 병렬 실행 힌트일 뿐 보안 장치가 아님; allowed_tools는 자동 승인 목록일 뿐, 쓰기 통제는 disallowed_tools, can_use_tool, PreToolUse 훅(6장)
- 핵심 메시지: readOnlyHint를 잘못 붙이면 쓰기는 그대로, 경쟁 상태만 생긴다
- 출처: 출처: Anthropic, Claude Agent SDK reference (Python); How the agent loop works (Agent SDK)

<!-- 노트: 인프로세스란 별도 프로세스 없이 내 파이썬 프로세스 안에서 도구 함수가 실행된다는 뜻이고, 함수 팩토리로 감싼 것은 반복문의 늦은 바인딩 문제를 피하기 위해서입니다. docs_search와 ticket_lookup은 readOnlyHint=True라 한 턴에 함께 요청되면 동시에 실행되고 ticket_update는 순서대로 실행되며, 3.6의 execute_tool_calls도 ToolSpec.read_only를 보고 같은 규칙을 따릅니다. call_id는 임의 ID라 트랜스크립트와의 연결은 훅의 tool_use_id로 합니다(6장, 9장). 데모에서는 disallowed_tools로 Bash, Read 같은 내장 도구를 끄고 짧은 system_prompt로 역할을 고정했습니다. -->

## 12. 공통 실행기 execute_tool()

- 패턴: `code`
- 리드문: 모든 도구 호출이 한곳을 지나며 실패를 모델용 결과로 바꾼다

```python
async def execute_tool(name, tool_use_id, raw, reg, ctx):
    spec, status = reg.get(name), "ok"  # 미등록 처리 생략
    try:
        args = spec.input_model.model_validate(raw)
        text = await asyncio.wait_for(
            _invoke(spec.fn, args), timeout=spec.timeout_s)
    except ValidationError as e:  # 교재는 ToolError로 바꿔 다시 던짐
        status, text = "invalid_input", _validation_message(e)
    except TimeoutError:
        status, text = "timeout", "범위를 좁혀 다시 호출하세요"
    except ToolError as e: status, text = "error", str(e)
    except Exception: status, text = "error", "내부 오류 안내"
    content, art_id, path = _cap(text, ctx, tool_use_id)
    _audit(ctx, {...})  # 이후 is_error를 붙여 반환
```

- 보조 설명: 흐름: 도구 확인 → 입력 검증 → 실행(3초 제한) → 4KB 상한 → 감사 로그; _validation_message가 내부 타입 표기, none_required 오류, 'Value error, ' 접두어를 지움; 4KB 초과 시 앞뒤 1.5KB만 남기고 모델에는 artifact_id만, 서버 경로는 감사 로그에만; 동기 함수는 스레드를 멈출 수 없어 I/O에 타임아웃(7장), 읽기 전용 호출은 asyncio.gather로 병렬
- 핵심 메시지: execute_tool()은 절대 예외를 던지지 않는다
- 출처: 출처: 교재 harness/executor.py 요약(구조 단순화)

- 패턴: `summary`
