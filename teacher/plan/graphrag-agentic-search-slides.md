## 슬라이드 1. 워크플로우 도식
- 제목: GraphRAG Agentic 검색: 3단계 Opus 에이전트가 툴을 골라 부르는 ReAct 고리
- 리드문: 검색은 툴로 열어 Opus가 고르고, 2, 5, 7단계 판단은 의사결정AI(Jev)가 확률로, 막는 일은 코드가 맡음
- 노드 요청: 동기 요청 | 질문 + 역할
- 노드 1: 1 | 요청 접수, 준비 확인
- 노드 2: 2 | 질문 분석(Jev)
- 노드 3: 3 | 검색 에이전트(Opus)
- 노드 4: 4 | 툴 실행
- 노드 5: 5 | 채점과 상한 판정(Jev)
- 노드 6: 6 | 리랭킹
- 노드 7: 7 | 수집 종료 판정(Jev)
- 노드 8: 8 | 답변 생성
- 노드 9: 9 | 근거 검증(규칙)
- 툴 상자: 4단계의 툴 | 검색 툴 5개 + finish(5장)
- 종료 오류: 10 | 오류
- 종료 불필요: 10 | 검색 불필요
- 종료 확인: 10 | 확인 필요(clarify)
- 종료 근거: 10 | 검색 결과, 확인할 수 없음
- 종료 완료: 10 | 답변 완료, 확인 필요(2회 소진)
- 종료 실패: 10 | 생성 실패(근거 목록만)
- 화살표 글: 설정, 권한 오류 | 인사, 잡담 | 질문이 모호함 | finish, 강제 종료 | 답변 켬
- 반복 글: 반복 1, 툴 호출 회차 최대 6 | 반복 2, 재작성 최대 2회
- 범례: 생성형AI | 예측형AI | 규칙기반 | 서브 워크플로우 | 종료 상태
- 화면 출처: teacher/plan/graphrag-react-search.md 1장, 벡터 검색 Agentic 워크플로우(교재)
- 상세 보기 링크: #1-메인-워크플로우-단계-1--10
- 발표자 노트:
  - 3단계가 ReAct 고리입니다. 에이전트가 생각하고, 툴을 부르고(4단계), 코드가 채점과 상한을 판정해(5단계) 다시 에이전트에게 돌려줍니다.
  - 질문 변환 단계는 없어졌습니다. 질의를 다시 쓰거나 나누는 일은 에이전트가 툴 인자로 바로 합니다. 그래서 단계 번호를 1 ~ 10으로 다시 매겼습니다.
  - 상한에 걸리면 모델을 다시 부르지 않고 5단계 코드가 종료 상태를 정해 6단계로 보냅니다.
  - 3단계는 사용자 결정에 따라 Claude Opus 5.5를 씁니다. 2, 5, 7단계는 의사결정AI TypeSafe Jev가 확률을 내고 코드가 문턱값으로 정합니다(3장). Global 검색 안의 G1, G2와 8단계 답변은 현행 LLM(Groq)입니다.

## 슬라이드 3. 의사결정AI란
- 제목: 의사결정AI TypeSafe Jev: 글 대신 형이 정해진 답과 확률을 돌려줌
- 리드문: 「System One」 모델. 자료와 질문을 한 요청으로 보내면 질문마다 따로 판정하고, 결정은 우리 코드가 문턱값으로 내림
- 흐름 제목: Jev 호출
- 흐름: 자료(state) + 형이 정해진 질문 | Jev: 질문마다 따로, 동시에 판정 | 답 + 확률 + confidence | 코드가 문턱값으로 결정
- 흐름 설명: POST https://api.typesafe.ai/v1/systemone(Bearer 인증). 글을 만들지 않으므로 결과를 파싱할 필요가 없음
- 표 열 너비: [1.5, 3.2, 3.5]

| 질문 형 | 돌려주는 것 | 이 워크플로우에서 |
|---|---|---|
| Choice | 보기 중 하나 + 보기별 확률 + confidence | 2단계 첫 툴 후보 |
| Score | 단계 점수 + 확률 + confidence | 쓰지 않음 |
| Noul | 참일 확률 0 ~ 1(confidence 없음) | 잡담인가, 원문이 관련 있나, 전제와 어긋나나 |

- 콜아웃: 2, 5, 7단계는 규칙 + Jev. 질의문을 지어야 하는 3단계는 Opus
- 카드 제목: 알고 쓸 것(공식 문서)
- 카드:
  - 입력 100만 토큰당 $0.042, 출력 무료. 요청당 64k, 질문당 32k 토큰
  - jev-latest는 jev-1.14.0(2026-10-14). 문턱값을 맞췄으면 버전 고정
  - 확률은 보정됨(여러 답을 모았을 때). 답 하나가 맞다는 보장은 아님
  - 문턱 출발점: Choice confidence 0.5 미만은 불확실, Noul 0.7 이상 예, 0.3 이하 아니오
  - 영어가 가장 정확. 한국어는 시험하고 confidence를 지켜봄
  - 약점(세기, 숫자, 날짜, 여러 단계 건너 묻기, 첫 보기 쏠림, 글 만들기)은 코드가 맡음
- 화면 출처: docs.typesafe.ai(Introduction, System One, Primitives, Models, Confidence, Jev 1.13 jaggedness, 2026-10-25 확인)
- 상세 보기 링크: #7-의사결정aijev-적용-2-5-7단계
- 발표자 노트:
  - 의사결정AI는 LLM처럼 자연어를 읽지만 글을 쓰지 않습니다. 우리가 정한 보기나 예, 아니오 중에서 고르고, 그 확률을 돌려줍니다. TypeSafe는 이런 모델을 「System One」이라 부르고, Jev가 첫 모델입니다.
  - 질문 하나에 판단 하나만 담고, 여러 판단은 코드에서 합칩니다. 한 요청에 질문을 여러 개 넣어도 질문마다 따로 판정하므로 서로 섞이지 않습니다.
  - 공식 문서가 밝힌 약점(셈, 숫자, 날짜, 첫 보기 쏠림)은 설계에서 코드로 돌렸습니다. 예를 들어 NO_NEW는 Jev 판정을 코드가 셉니다.
  - 이 장은 TypeSafe 공식 문서만 근거로 했습니다. 지연 시간은 공식 수치가 없어 측정이 필요합니다.

## 슬라이드 4. 2단계 질문 분석과 첫 툴 후보
- 제목: 2단계 질문 분석: 식별자는 코드가 바꾸고, Jev가 잡담, 모호함, 첫 툴 후보를 판정함
- 리드문: 문항 유형마다 예상되는 툴 경로를 첫 툴 후보로 넘기되, 툴을 실제로 고르는 일은 3단계 Opus가 함
- 표 열 너비: [2.6, 2.9, 9.4]

| 유형 | 문항 | 예상 툴 경로 |
|---|---|---|
| 약관 사실 | Q01 ~ Q06 | local_search 또는 search_chunks → finish |
| 카드 혜택 | Q07 ~ Q13 | local_search(카드 필터 자동) → finish |
| 회원 상담 | Q14 ~ Q17 | find_entities(가명 id) → get_source_chunks, 또는 local_search |
| 함정 | Q18 ~ Q22 | local_search → NO_COOCCUR → finish(unverifiable) |
| 경향 | Q23, Q24 | global_search → finish |
| 혼합 | Q25 | global_search → 미확인 주제만 local_search(topic_id) |

- 규칙 카드 제목: 2단계가 하는 일
- 규칙 카드:
  - 코드: 회원번호 → 가명 id, 카드명 → card_id. 모든 툴의 필터가 됨. Jev에는 식별자를 지운 질문만 보냄
  - Jev Noul: 잡담 또는 모호함이 0.7 이상이면 종료(검색 불필요, 확인 필요). 애매하면 검색으로
  - Jev Choice: 첫 툴 후보는 confidence 0.5 이상이고 보기 순서를 뒤집어도 같을 때만 넘김
- 화면 출처: teacher/plan/graphrag-react-search.md 2-4절, 7-2절
- 상세 보기 링크: #2-4-문항-유형별-예상-경로
- 발표자 노트:
  - v1.2에서 Opus(effort low)가 하던 일을 사용자 결정으로 Jev로 바꿨습니다. 잡담인가, 모호한가, 첫 툴은 무엇인가는 답이 정해진 판단이라 글을 만들 필요가 없고, 비용도 거의 들지 않습니다.
  - Jev는 Choice의 첫 보기로 쏠릴 수 있다고 공식 문서가 밝힙니다. 그래서 보기 순서를 뒤집어 한 번 더 묻고, 답이 같을 때만 첫 툴 후보로 씁니다. 후보는 권고일 뿐 에이전트가 따르지 않아도 됩니다.
  - 함정 질문은 에이전트가 sufficient로 끝내도 7단계 재확인이 막습니다.

## 슬라이드 5. 검색 툴 집합
- 제목: 4단계 검색 툴: 묶음 툴 3개, 단위 툴 2개, 종료 툴 1개
- 리드문: 모든 툴 입력에서 필터 칸을 없애, 세대와 식별자는 래퍼가 강제로 붙임
- 표 열 너비: [3.0, 3.6, 6.0, 2.3]

| 툴 | 입력 | 하는 일 | 안의 단계 |
|---|---|---|---|
| search_chunks | query | 벡터 + BM25 → RRF → 리랭킹 → 청크 최대 6 | O1 ~ O4 |
| local_search | query, topic_id | 청크 → 엔티티 축소 → 1-hop 이웃 → 보고서 | L1 ~ L4 |
| global_search | question | 보고서 고르기 → 주제와 Follow-up → 주제별 Local | G1 ~ G3 |
| find_entities | text | 레이블별 키로 엔티티 → 1-hop 이웃(원문 없음) | 새 툴 |
| get_source_chunks | entity_ids, with_reports | 엔티티의 원문 청크, 보고서 | L 일부 |
| finish | status, reason | 수집 종료(충분, 확인 불가, 확인 필요) | - |

- 화면 출처: teacher/plan/graphrag-react-search.md 2-1, 2-2절
- 상세 보기 링크: #2-1-툴-집합
- 발표자 노트:
  - find_entities는 「이름 정확 일치」로 설계했다가 바꿨습니다. 그래프에 공통 이름 속성이 없기 때문입니다(카드는 card_name, 조항은 clause_no, 상담은 record_id). 회원 노드도 없어서, 회원은 Consultation 노드를 가명 id로 찾습니다.
  - G1, G2까지만 하는 search_communities 툴은 두지 않습니다(v1.4). global_search와 차이가 G3 자동 여부뿐이라 겹치는 툴이 모델의 선택을 흔들기 때문입니다. 원문을 못 찾은 주제는 local_search(topic_id)로 보충합니다. global_search는 요청당 1번입니다.
  - search_chunks는 Advisor가 local_search와 겹친다며 빼자고 했지만, 사용자 요구(검색엔진 검색 툴)라 남겼습니다. 대신 7단계가 어느 툴로 모았든 그래프 연결을 직접 찾습니다.

## 슬라이드 6. 5단계 채점 신호와 권장 행동
- 제목: 5단계 채점 신호: 코드 신호에 Jev 원문 판정을 더해 에이전트의 관찰로 돌려줌
- 리드문: 신호의 뜻과 권장 행동은 시스템 프롬프트로 알려 주고, 세는 일과 반드시 막을 일은 코드가 맡음
- 표 열 너비: [3.2, 6.6, 5.1]

| 신호 | 판정 규칙(가정값) | 에이전트 권장 행동 |
|---|---|---|
| PASS | local: 포함률 0.6 이상, 원문 2개 이상. global: 관련 보고서 2개 이상, 주제마다 원문 | finish(sufficient) |
| NO_COOCCUR | 핵심 명사 두 개가 한 문장에 함께 나온 근거 0건 | 하위 질의로 local_search 1번, 남으면 finish(unverifiable) |
| NO_SEED | 검색 결과 0건 | 질의를 다시 써서 local_search |
| LOW_COVERAGE | 포함률 0.6 미만 | 복합 질문은 나눠서, 단순 질문은 다시 써서 local_search |
| SCATTERED | 원문이 문서 3종 이상, 포함률 0.6 미만 | global_search |
| NO_REPORTS, OFF_TOPIC_REPORTS | 보고서 0건, 관련도 최댓값 0.25 미만 | local_search로 사실부터 |
| NO_NEW | Jev가 관련 있다고 본(0.45 이상) 새 원문 0건 | finish. 2회 연속이면 코드가 강제 종료 |
| Jev 원문 판정 | 원문마다 관련(0.45 미만 뺌), 답 근거(0.55 초과), 전제 충돌, 지시 끼워 넣기(0.7 초과 뺌) | 근거 표시를 보고 finish 또는 다시 검색 |

- 발표자 노트:
  - 신호 정의는 v2.2 설계를 그대로 씁니다. 관련도는 질문과 보고서 요약 임베딩의 코사인 유사도이며 LLM이 점수를 내지 않습니다.
  - 질의 없는 툴(get_source_chunks)의 결과도 원 질문 기준으로 다시 채점해 신호를 붙입니다.
  - Jev 원문 판정의 문턱값(0.45, 0.55, 0.7)은 공식 쿡북(Classifying RAG passages)의 출발값입니다. 한국어 원문이라 평가셋으로 다시 맞춥니다. ID_MISMATCH 같은 필터 신호는 7장 안전 장치에서 다룹니다.

## 슬라이드 8. 툴 안의 서브 워크플로우와 검색엔진 검색(O)
- 제목: 툴 안의 서브 워크플로우: 바닥은 검색엔진 검색(O)
- 리드문: 툴은 v2.2의 O, L, G 함수를 그대로 감싸므로, v2.2를 먼저 구현하면 버리는 코드가 없음
- 쌓임 1: Global 검색(G) | global_search(G1 ~ G3)
- 쌓임 2: Local 검색(L) | local_search(L1 ~ L4), get_source_chunks(L 일부)
- 쌓임 3: 검색엔진 검색(O) | search_chunks(O1 ~ O4). L1이 이것을 부름
- 흐름 제목: 검색엔진 검색(O)
- 흐름: O1 벡터 검색 → 최대 25 | O2 BM25 검색 → 최대 25 | O3 RRF → 중복 제거 25 | O4 리랭킹 → 최대 6
- 흐름 설명: 같은 질의로 O1과 O2를 병렬 실행. 식별자 필터와 세대를 두 쪽에 똑같이 걸고, 필터로 후보가 6개 이하면 O4를 건너뜀
- 결정 카드 제목: 최적안 결정
- 결정 카드:
  - O3 RRF는 코드에서. O1, O2 중 한쪽이 죽어도 남은 순위로 부분결과를 냄. OpenSearch 파이프라인 RRF는 선택지로 남김
  - O4 리랭커는 Cohere rerank-v4.0-fast. RAG 실습 코드와 같고 6단계 리랭킹에서도 같은 리랭커를 씀
- 화면 출처: teacher/plan/graphrag-agentic-search.md 4, 4-1절
- 상세 보기 링크: https://github.com/unicorn-campus/hybrid-ai/blob/main/teacher/plan/graphrag-agentic-search.md#4-1-검색엔진-검색o-벡터-검색--bm25-검색--rrf--리랭킹
- 발표자 노트:
  - 툴 안의 서브 워크플로우는 v2.2 설계(4장)를 그대로 씁니다. 단계 번호만 메인 워크플로우와 다르게 O, L, G 접두어를 붙입니다.

## 슬라이드 10. Global 검색(G)
- 제목: Global 검색(G): global_search가 G1 ~ G3을 한 번에 함
- 리드문: 보고서 고르기와 Follow-up 질문은 현행 Groq 모델이 하고, 주제마다 원문 근거를 붙임
- 흐름 제목: Global 검색(G)
- 흐름: G1 커뮤니티 검색 → 보고서 ≤ 12 | G2 주제와 Follow-up → 1 ~ 5개 | G3 주제별 Local 검색(병렬)
- 흐름 설명: global_search가 G1 ~ G3을 한 번에 함. 원문을 못 찾은 주제는 에이전트가 local_search(topic_id)로 보충
- 카드 1 제목: G1 커뮤니티 검색(보고서 고르기)
- 카드 1:
  - 보고서 제목 78개(약 1,150 토큰)를 LLM에 보이고 관련 보고서를 고르게 함. 상한 12
  - 보고서 본문 몫은 12,000 토큰. 고른 뒤 실제로 세고, 넘으면 관련도 낮은 보고서부터 뺌
  - 모델은 현행 Groq(v2.2와 같음). 실패하면 보고서 벡터 상위 5개
- 카드 2 제목: G2 주제와 Follow-up 질문
- 카드 2:
  - 고른 보고서를 주제 1 ~ 5개로 묶어 주제 id를 붙이고, 주제마다 「사실로 확인할 것」을 하나씩
  - local_search(topic_id)의 채점 기준은 그 주제의 Follow-up 질문(원 질문이 아님)
  - 원문을 못 찾은 주제는 답에서 미확인으로 표시
- 화면 출처: teacher/plan/graphrag-agentic-search.md 4-3절, teacher/plan/graphrag-react-search.md 2-2절, 5장
- 상세 보기 링크: https://github.com/unicorn-campus/hybrid-ai/blob/main/teacher/plan/graphrag-agentic-search.md#4-3-global-검색g-커뮤니티-검색--follow-up-질문--follow-up-local-검색
- 발표자 노트:
  - 이 실습의 Global은 자체 구성입니다. Microsoft Global Search(map-reduce)와 다르고, DRIFT와 닮았지만 같은 구현은 아닙니다.
  - G1, G2는 현행 Groq 모델로 둡니다(사용자 결정). Advisor는 검색 경로 결정이라며 Opus를 권했지만 받지 않았습니다. v2.2와 같은 모델이라 프롬프트와 실패 대체를 그대로 씁니다.
  - 벡터 상위 5개로 고르면 상담 계열 보고서 12개 중 최대 5개만 담깁니다(포함 상한 5/12, 계산값).
