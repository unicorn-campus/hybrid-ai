# 하네스 엔지니어링, AI 시스템에 적용하는 방법

이 문서는 슬라이드 덱 「하네스 엔지니어링」 34장과 1:1로 짝을 이루는 상세 교재임.  
슬라이드의 「상세 보기」 링크가 이 문서의 각 절(1-1 ~ 6-6)로 이어짐.  
슬라이드에는 줄여서 담은 내용을 여기서 풀어 쓰고, 어려운 용어는 처음 나올 때 괄호로 풀이함.

## 모듈 소개

- 대상: 멀티 에이전트 시스템(MAS) 개념과 LangGraph 기초를 배운 개발자  
- 위치: 「Agentic AI 핵심이해」 교재 141 ~ 145쪽(앞선 교재)을 대체하는 독립 모듈  
- 핵심 질문: 모델은 그대로인데, 모델 바깥의 무엇을 설계해야 에이전트가 잘하고 사고 없이 일하는가  
- 용어 약속: 하네스(harness)는 에이전트에서 모델(LLM)을 뺀 모든 것을 뜻함

## 학습 목표

1. 하네스가 무엇인지, 같은 모델의 결과를 왜 바꾸는지 설명할 수 있음  
2. 하네스 4층(미리 안내, 결과 확인, 실행 중 통제, 관측과 개선)으로 장치를 나눠 볼 수 있음  
3. 보안을 필터(걸러 내기)가 아니라 구조(애초에 위험한 조합을 만들지 않기)로 설계할 수 있음  
4. 최소 하네스로 시작해 실패를 보며 키우고, 모델이 바뀌면 줄이는 절차를 따라 할 수 있음

## 1장. 하네스 엔지니어링이란

### 1-1 같은 모델, 다른 결과

모델은 그대로 두고 주변 환경(하네스)만 바꿔도 에이전트의 성적이 크게 달라짐.

**쉬운 설명**

같은 선수라도 어떤 코치, 장비, 경기장에서 뛰느냐에 따라 기록이 달라지는 것과 같은 이야기임.  
(비유가 맞지 않는 점: 선수는 좋은 환경에서 연습하며 실력 자체가 늘지만, 모델의 실력은 그대로이고 결과만 달라짐.)  
LangChain 팀은 코딩 에이전트의 모델(gpt-5.2-codex)을 고정한 채 시스템 프롬프트, 도구, 미들웨어만 고쳤음.  
미들웨어(middleware)는 모델과 도구 사이에서 정해진 시점에 끼어들어 검사하는 코드를 말함.  
그 결과 Terminal Bench 2.0 점수가 52.8에서 66.5로 13.7점 올랐고, 순위는 30위권에서 5위권으로 올라갔음.  
2026년 5월의 입장 논문(Zhang 외)은 하네스를 밝히지 않은 채 모델끼리 비교하면 안 된다고 주장함.  
같은 모델도 하네스에 따라 순위가 뒤바뀔 수 있기 때문임.  
이 논문이 인용한 사례에서는 Terminal-Bench 2의 pass@1 점수가 69.7%에서 77.0%로 올랐음(모델 고정).

| 사례 | 바꾼 것 | 점수 변화 | 조건 |
|---|---|---|---|
| LangChain 코딩 에이전트 | 하네스만 | 52.8 → 66.5 | Terminal Bench 2.0, 모델 고정 |
| 하네스 공개 촉구 논문의 인용 사례 | 하네스만 | 69.7% → 77.0% | Terminal-Bench 2 pass@1, 모델 고정 |

하네스가 결과를 바꾸는 길은 세 갈래로 나눠 볼 수 있음. 이 세 갈래가 이 모듈의 뼈대임.  
1. 무엇을 보여 주나: 지침, 환경 정보, 컨텍스트(모델에 넣어 주는 정보). 2장에서 다룸  
2. 무엇을 할 수 있나: 도구, 권한, 실행 환경. 4장에서 다룸  
3. 언제 확인하고 멈추나: 검증, 종료 조건. 3장과 4장에서 다룸

반대 의견도 있음. 하네스의 효과가 작다는 결과는 1-5에서 함께 봄.

### 1-2 Agent = Model + Harness

하네스는 에이전트에서 모델을 뺀 모든 것임.

**쉬운 설명**

모델(LLM)은 글을 만들어 낼 뿐임. 도구를 실제로 실행하고, 결과를 다시 모델에 넣어 주고, 언제 멈출지 정하는 일은  
모두 하네스가 맡음. 그래서 "에이전트 = 모델 + 하네스"라고 적음.  
하네스에는 여덟 가지 부품이 들어감: 지침, 도구, 컨텍스트, 상태 저장, 샌드박스, 검증, 권한과 승인, 트레이스와 평가.  
샌드박스(sandbox)는 문제가 생겨도 바깥에 피해가 번지지 않도록 격리한 실행 공간임.  
트레이스(trace)는 에이전트가 한 모든 일의 기록임(5-1에서 자세히 봄).

하네스가 하는 일은 두 가지로 나뉨.

| 하는 일 | 내용 | 대표 장치 |
|---|---|---|
| 잘하게 만들기 | 원하는 결과를 내도록 모델을 돕는 일 | 지침, 도구, 컨텍스트, 검증 |
| 사고 안 나게 막기 | 피해가 생기지 않도록 막는 일 | 종료 조건, 권한, 샌드박스, 사람 승인 |

Hugging Face 용어집은 "하네스"의 뜻을 둘로 나눔.  
좁은 뜻은 모델을 부르고 도구를 실행하는 실행 계층이고, 넓은 뜻은 모델을 뺀 전부임. 이 모듈은 넓은 뜻을 씀.

**앞선 교재와 달라진 점**  
- 앞선 교재의 정의("안전하고 예측 가능하게 동작하도록 실행 환경 전체를 설계")는 위 표의 두 번째 줄에 해당함.  
- 최신 자료는 첫 번째 줄(잘하게 만들기)도 하네스의 절반으로 봄. 그래서 정의를 두 갈래로 넓혔음.

### 1-3 프롬프트, 컨텍스트, 하네스

관심이 "무엇을 말할까"에서 "어떤 환경에서 일하게 할까"로 넓어졌음.

**쉬운 설명**

처음에는 지시문 한 번을 잘 쓰는 일(프롬프트 엔지니어링)이 중요했음.  
에이전트가 여러 번 돌면서 도구 결과와 이력이 쌓이자, 모델에 무엇을 보여 줄지가 더 중요해졌고  
이를 컨텍스트 엔지니어링이라고 불렀음. 컨텍스트(context)는 모델이 한 번에 읽는 정보 전체를 뜻함.  
하네스 엔지니어링은 여기에 실행 환경, 검증, 권한, 개선 습관까지 더함.  
국내 언론도 이 세 단계를 같은 순서로 소개함.

| 단계 | 묻는 질문 | 다루는 범위 | 예 |
|---|---|---|---|
| 프롬프트 엔지니어링 | 어떻게 지시할까 | 지시문 한 번 | 역할, 형식, 예시 |
| 컨텍스트 엔지니어링 | 무엇을 보여 줄까 | 모델에 들어가는 정보 전체 | 검색 결과, 이력, 도구 결과 |
| 하네스 엔지니어링 | 어떤 환경에서 일하게 할까 | 실행 환경, 도구, 검증, 권한, 개선 | 테스트, 승인, 트레이스 |

세 단계는 서로 바꿔 쓰는 것이 아님. 다음 단계가 앞 단계를 버리는 것이 아니라 안에 품음.  
(바깥 단계일수록 범위가 넓은 동심 사각형으로 그리면 쉬움.)

### 1-4 하네스 4층 지도

하네스는 미리 안내하고, 결과를 확인하고, 실행 중에 막고, 기록을 보고 고치는 4층으로 나눠 볼 수 있음.

**쉬운 설명**

이 그림이 모듈 전체의 지도임. 장치가 많아 보여도 어느 층의 일인지 따지면 정리됨.  
1층과 2층은 Böckeler가 말한 가이드(미리 안내)와 센서(사후 확인)임.  
3층은 앞선 교재의 9대 실행 리스크 해결책이 들어가는 자리임. 4층은 이 모두를 고쳐 나가는 습관임.

| 층 | 이름 | 하는 일 | 대표 장치 | 장 |
|---|---|---|---|---|
| 1층 | 미리 안내(가이드) | 시작 전에 방향을 줌 | 지침 파일, 도구 계약, 컨텍스트, 상태 저장 | 2장 |
| 2층 | 결과 확인(센서) | 한 일을 확인하고 되돌림 | 테스트, 스키마 검증, 평가 에이전트 | 3장 |
| 3층 | 실행 중 통제(가드레일) | 사고를 실행 중에 막음 | 반복 상한, 예산, 권한, 사람 승인 | 4장 |
| 4층 | 관측과 개선 | 기록을 보고 하네스를 고침 | 트레이스, 평가셋, 조향 루프 | 5장 |

4층에서 1 ~ 3층으로 되돌아가는 화살표를 조향 루프라고 부름(5-3).  
가드레일(guardrail)은 도로 가장자리 난간처럼 선을 넘지 못하게 막는 장치를 뜻함.

핵심 원칙은 "통제는 코드가 집행한다"임.  
- 권한과 상한은 모델 바깥의 규칙이 검사함  
- 모델이 지시를 우회하려 해도 넘을 수 없음  
- 허용 여부를 LLM에 묻지 않음

**앞선 교재와 달라진 점**  
- 앞선 교재 141쪽 그림의 Supervisor 상자는 이 지도에서 3층의 "하네스 런타임"에 해당함.  
- 이름 때문에 감독 에이전트(LLM)로 오해하기 쉬움. 예산 초과나 반복 감지로 실행을 끊는 일은 코드 규칙이 맡아야 함.  
- KISA 안내서도 허용 여부를 LLM에 맡기지 말고 연결된 시스템에서 권한을 검사하라고 권함.

### 1-5 하네스의 한계와 반론

하네스는 모델이 좋아지면 낡음. 더하는 만큼 빼는 일도 설계해야 함.

**쉬운 설명**

하네스가 만능이라는 이야기가 아님. 반론과 한계를 함께 알아야 균형 있게 쓸 수 있음.  
Latent Space는 "하네스 엔지니어링은 실체가 있나"라는 논쟁을 정리했음.  
한 벤치마크에서는 같은 모델을 여러 하네스에 넣었을 때 차이가 오차 범위 안이었음.  
ETH Zurich 연구는 AGENTS.md 같은 컨텍스트 파일이 대체로 성공률을 높이지 못하고 비용만 20% 넘게 늘린다고 보고했음.  
다만 표준과 다른 작업 방식을 알려 줄 때는 쓸모가 있었음.  
Anthropic은 이전 모델이 컨텍스트 한계에 가까워지면 서둘러 끝내는 버릇이 있어 컨텍스트 리셋 장치를 넣었음.  
Opus 4.5에서는 이 버릇이 거의 사라져 그 장치를 통째로 뺐음.

| 반론과 한계 | 내용 | 그래서 이렇게 |
|---|---|---|
| 하네스 차이가 작다는 결과도 있음 | 같은 모델을 여러 하네스에서 돌려도 차이가 오차 범위라는 벤치마크가 소개됨 | 효과는 평가로 확인한 뒤 남김 |
| 지침 파일이 늘 돕지는 않음 | 컨텍스트 파일은 대체로 성공률을 높이지 못하고 비용만 20% 넘게 늘림 | 가볍게 시작함 |
| 하네스는 낡음 | 새 모델이 서두르는 버릇을 고치자 컨텍스트 리셋 장치가 필요 없어짐 | 모델이 바뀌면 하나씩 빼 봄(5-5) |

결론은 하네스가 쓸모없다는 것이 아님. 필요한 만큼만 두고, 효과를 재고, 모델이 바뀌면 다시 보라는 뜻임.

## 2장. 1층 미리 안내

### 2-1 가이드: 미리 안내

실수를 미리 막는 안내(가이드)와 실수를 잡아내는 검사(센서)가 짝을 이룸.

**쉬운 설명**

Böckeler는 하네스 장치를 가이드와 센서로 나눔.  
가이드(feedforward)는 에이전트가 행동하기 전에 원하는 방향을 알려 주고,  
센서(feedback)는 행동한 뒤 결과를 보고 스스로 고치게 함.  
2장은 가이드를, 3장은 센서를 다룸.

| 구분 | 시점 | 하는 일 | 예 |
|---|---|---|---|
| 가이드(feedforward) | 행동 전 | 방향을 줌 | 지침 파일, 규칙, 스킬, 도구 설명, 템플릿 |
| 센서(feedback) | 행동 뒤 | 결과를 확인함 | 테스트, 린터, 스키마 검증, 평가 에이전트 |

린터(linter)는 코드가 정해 둔 규칙을 지켰는지 자동으로 검사하는 도구임.  
센서가 틀렸다고 알려 주면 에이전트가 고치도록 되돌려 보냄.  
가이드만 있으면 에이전트가 지켰는지 알 수 없고, 센서만 있으면 같은 실수를 반복함. 그래서 둘을 함께 설계함.

**더 알아보기**  
- Böckeler, Harness engineering for coding agent users(martinfowler.com, 2026-04-02)  
  https://martinfowler.com/articles/harness-engineering.html

### 2-2 지침 파일은 목차처럼

지침 파일은 짧은 지도로 두고, 코드만 봐서는 알 수 없는 규칙만 적음.

**쉬운 설명**

지침 파일(AGENTS.md 같은 파일)은 에이전트가 작업 전에 미리 읽는 업무 안내서임.  
OpenAI Codex 팀은 처음에 큰 지침 파일 하나를 썼다가 실패했음.  
컨텍스트가 부족해지고, 규칙이 금방 낡고, 사람이 관리하지 않게 됐기 때문임.  
그래서 AGENTS.md를 100줄 안팎의 목차로 줄이고, 자세한 내용은 문서 폴더(`docs/`)에 나눠 두었음.  
문서가 맞는지는 린터와 CI(코드를 올릴 때마다 자동으로 돌리는 검사)가 기계적으로 확인함.  
정기 문서 정리 에이전트가 낡은 문서를 고침.

| 실패한 방식: 거대한 지침 파일 하나 | 바꾼 방식: 목차 + 문서 폴더 |
|---|---|
| 컨텍스트를 잡아먹어 정작 할 일을 놓침 | AGENTS.md 약 100줄 = 목차 |
| 모두 중요하면 아무것도 중요하지 않음 | `docs/`에 설계 문서, 실행 계획, 규칙 = 자세한 내용 |
| 금방 낡고, 무엇이 맞는지 알 수 없음 | 린터와 CI가 문서의 연결과 최신 상태를 검사 |
| 기계로 검사하기 어려움 | 정기 문서 정리 에이전트가 낡은 문서를 고침 |

ETH 연구(2026) 결과도 같은 방향임. 저장소 개요 설명은 도움이 안 되고,  
표준과 다른 작업 방식을 알릴 때만 쓸모 있었음.  
그래서 에이전트가 코드를 읽으면 알 수 있는 내용은 지침에 다시 쓰지 않음.

### 2-3 도구 계약 설계

도구는 좁은 기능만 주고, 입력과 오류를 분명히 약속함.

**쉬운 설명**

도구 계약은 "이 도구는 무엇을 받아 무엇을 돌려주는가"를 분명히 정한 약속임.  
Anthropic은 사람이 쓰는 화면(UI)을 설계하듯 에이전트가 쓰는 도구 인터페이스도 공들여 설계하라고 권함.  
설명, 예시, 실수하기 어려운 매개변수가 핵심임.  
도구 계약은 1층(가이드)이면서 3층(통제)의 첫 방어선이기도 함.

| 관점 | 피할 것 | 권장 | 이유 |
|---|---|---|---|
| 기능 범위 | 셸 실행처럼 무엇이든 되는 도구 | 파일 쓰기만, 메일 읽기만 같은 좁은 도구 | 할 수 있는 일이 적을수록 사고도 작음 |
| 권한 | 읽기, 쓰기, 삭제를 한 번에 | 필요한 권한만(읽기 전용 범위 등) | 잘못 써도 피해가 좁음 |
| 입력 | 자유 문자열 | 형식이 정해진 매개변수 | 잘못된 입력을 미리 거름 |
| 오류 응답 | 내부 오류를 그대로 | 무엇이 틀렸고 어떻게 고칠지 | 에이전트가 읽고 스스로 고침 |
| 설명 | 이름만 | 언제 쓰는지, 예시, 주의점 | 모델이 알맞은 때에 고름 |

**사례: 메일 요약 에이전트** (KISA 안내서의 "과도한 대행" 사례)  
- 메일 요약용 플러그인에 '보내기' 기능까지 들어 있었음  
- 악성 메일 한 통이 에이전트를 속여 스팸을 발송했음  
- 대책: 읽기 전용 도구, 읽기 전용 권한, 발송은 사람 확인  
- 요약만 하면 되는데 보내기까지 줬기 때문에 사고가 났음. 기능, 권한, 자율성 세 가지를 모두 줄이라고 권함

### 2-4 컨텍스트 관리

컨텍스트가 길어지면 비용도 오르고 정확도도 떨어짐.

**쉬운 설명**

토큰(모델이 글을 읽는 단위)이 늘수록 모델이 컨텍스트 안의 정보를 정확히 떠올리는 능력이 떨어짐.  
Anthropic은 이를 context rot(컨텍스트 부패)이라고 부름.  
그래서 컨텍스트 관리는 비용 문제이면서 품질 문제임.

| 기법 | 하는 일 | 주의 |
|---|---|---|
| 컴팩션 | 한계에 가까워지면 대화를 요약해 이어 감 | 중요한 내용이 빠질 수 있음 |
| 노트 남기기 | 진행 상황을 파일에 적고 필요할 때 다시 읽음 | 노트 형식을 정해 둠 |
| 도구 결과 지우기 | 다 쓴 도구 결과를 컨텍스트에서 뺌 | 다시 필요하면 다시 조회 |
| 서브에이전트 분리 | 깊은 조사는 서브에이전트가 하고 요약만 돌려줌 | 요약의 정확도를 확인 |
| 필요할 때만 검색 | 처음에 다 넣지 않고 파일 경로 같은 단서만 둠 | 검색 도구의 품질이 중요 |

서브에이전트(subagent)는 메인 에이전트가 일부 조사를 맡기는 보조 에이전트임.  
요약만 하면 중요한 내용을 잃을 수 있어서, 위 기법들을 함께 씀.  
다중 에이전트 실패 연구(MAST)도 "대화 이력 손실"을 실패 유형으로 꼽음.  
프롬프트 캐싱은 고정 지침을 앞에 두어 같은 내용을 반복해서 처리하는 비용을 줄임(앞선 교재 143쪽).

**앞선 교재와 달라진 점**  
- 앞선 교재 143쪽은 컨텍스트 관리를 비용 절감으로만 설명하고 "오래된 이력은 요약 후 전달"만 제시했음.  
- 이번에는 품질 문제로도 설명하고, 요약(컴팩션)의 약점을 보완하는 대안 네 가지를 더했음.

### 2-5 상태 저장과 이어 하기

컨텍스트 창이 바뀌어도 작업이 끊기지 않도록 상태를 바깥에 남김.

**쉬운 설명**

긴 작업은 컨텍스트 창 하나에 담기지 않음. 새 창에서 시작한 에이전트는 이전 일을 기억하지 못함.  
그래서 기억을 파일과 git(변경 이력을 남기는 도구)에 남겨야 함.  
Anthropic은 첫 세션에서 실행 준비 스크립트, 진행 기록 파일, 기능 목록을 만들고,  
이후 세션은 기능 하나씩만 구현하게 했음.  
기능 목록은 통과 여부 칸만 바꾸게 해서 에이전트가 목록을 함부로 지우지 못하게 했음.

| 역할 | 언제 | 하는 일 |
|---|---|---|
| 초기화 에이전트 | 1회 | 실행 환경 준비, 기능 목록 작성 |
| 코딩 에이전트 | 세션마다 반복 | 세션마다 기능 하나만 구현하고 확인 |

- `init.sh`: 실행 준비 스크립트  
- 진행 기록 파일  
- 기능 목록 JSON(통과 여부만 수정)  
- git 커밋

**MAS로 옮기면**  
- LangGraph 체크포인터(단계마다 상태를 저장하는 기능)로 단계마다 상태를 저장함

- Managed Agents 글은 세션 기록, 하네스, 샌드박스를 분리해 어느 하나가 멈춰도 다시 이어 가게 했다고 설명함

## 3장. 2층 결과 확인

### 3-1 센서의 두 종류

코드로 판정할 수 있는 검사를 먼저 쓰고, LLM 심사는 보조로 씀.

**쉬운 설명**

Böckeler는 센서를 연산형(computational)과 추론형(inferential)으로 나눔.  
연산형은 코드가 정답을 판정하고, 추론형은 LLM이 판단함.  
두 종류는 쓰임이 달라서 함께 쓰되, 싸고 확실한 코드 검사를 먼저 돌림.

| 구분 | 코드로 판정(연산형) | LLM이 판단(추론형) |
|---|---|---|
| 예 | 테스트, 린터, 타입 검사, 스키마 검증 | 평가 에이전트, LLM 심사 |
| 속도와 비용 | 빠르고 쌈 | 느리고 비쌈 |
| 결과 | 매번 같음 | 실행마다 다를 수 있음 |
| 잘 잡는 것 | 형식, 규칙, 동작 | 의미, 품질, 설계 취향 |

스키마(schema)는 데이터가 갖춰야 할 모양(필드 이름과 형식)을 정해 둔 틀임.  
스키마 검증은 그 모양을 만족하는지 코드로 확인하는 일임.

**앞선 교재와 달라진 점**  
- 앞선 교재 144쪽은 교차검증(다른 모델이나 프롬프트로 다시 검토)만 소개했음. 교차검증은 추론형 센서임.  
- 이번에는 그 앞에 코드로 확인할 수 있는 검사를 먼저 두라는 순서를 더했음.

**더 알아보기**

### 3-2 실제로 돌려 보고 확인

에이전트의 "다 했다"를 믿지 않고, 실행 결과로 확인함.

**쉬운 설명**

OpenAI Codex 팀은 계층 구조와 의존 방향(어느 부분이 어느 부분을 불러 쓸 수 있는지)을  
맞춤 린터와 구조 테스트로 강제했음.  
핵심은 린터 오류 메시지에 고치는 방법을 적어 둔 것임. 에이전트가 오류를 읽고 바로 스스로 고침.  
Anthropic은 단위 테스트만 통과하고 실제로는 안 되는 기능을 "완료"로 표시하는 문제를 겪었음.  
그래서 브라우저 자동화로 사람처럼 화면을 눌러 확인하게 했음.

| 확인 방법 | 하는 일 |
|---|---|
| 테스트 실행 | 기능이 실제로 동작하는지 확인 |
| 린터와 구조 테스트 | 계층 규칙, 이름 규칙, 파일 크기 같은 규칙을 기계로 강제 |
| 끝에서 끝까지 확인 | 브라우저로 사람처럼 화면을 눌러 봄 |

**고치는 방법을 담은 오류 메시지(이해를 돕기 위해 만든 예시임)**  
- 오류: domain 계층이 ui 계층을 불러옴  
- 고치는 법: 공용 타입은 types/ 폴더로 옮기고 그곳에서 불러올 것

오류 메시지가 "무엇이 틀렸는지"만 말하지 않고 "어떻게 고치는지"까지 말하는 점이 중요함.  
에이전트는 메시지를 읽고 판단하므로, 메시지 자체가 가이드(1층)의 역할을 겸함.

### 3-3 완료 기준을 먼저 합의

만드는 에이전트와 평가하는 에이전트를 나누고, 작업 전에 "끝"의 기준을 정함.

**쉬운 설명**

Anthropic은 생성 모델과 판별 모델이 겨루는 GAN에서 착안해 생성과 평가를 나눴음.  
평가 에이전트는 Playwright(브라우저를 자동으로 조작하는 도구)로 실제 앱 화면을 눌러 보고  
기준마다 점수와 비평을 씀.  
스프린트(짧은 개발 주기)마다 생성자와 평가자가 "다 됨"이 어떤 모습인지 먼저 합의함. 이것이 스프린트 계약임.  
평가자가 믿을 만하게 채점하도록 채점 기준과 예시를 따로 만들어 보정했음.

| 역할 | 하는 일 |
|---|---|
| 계획 에이전트 | 짧은 요청을 제품 명세로 늘림 |
| 생성 에이전트 | 기능을 만듦 |
| 평가 에이전트 | 실제 화면을 눌러 보며 기준별로 채점 |
| 스프린트 계약 | 코드를 쓰기 전에 "다 됨"의 모습을 둘이 합의 |

흐름은 계획, 생성, 평가 순이고, 평가에서 기준에 못 미치면 피드백을 주어 생성으로 되돌아감.

**왜 나누나**  
1. 만든 쪽이 스스로 평가하면 후해짐  
2. 평가자는 채점 기준과 예시로 따로 보정함  
3. 기준이 먼저 있어야 "다 했다"를 판정할 수 있음

**앞선 교재와 달라진 점**  
- 앞선 교재 144쪽의 교차검증 설명에는 생성과 평가를 나누는 패턴이 없었음. 이번에 더했음.

### 3-4 할루시네이션 전파 차단

검증을 통과한 결과만 다음 에이전트로 넘김.

**쉬운 설명**

할루시네이션(hallucination)은 모델이 사실이 아닌 내용을 그럴듯하게 만들어 내는 현상임.  
MAS에서는 한 에이전트의 잘못된 답이 다음 에이전트의 입력이 되어 번짐.  
그래서 에이전트 A와 B 사이에 검증 관문을 두고, 관문을 통과하지 못한 결과는 넘기지 않음.  
통과하지 못하면 재시도하거나 사람 확인으로 올림.  
앞선 교재 144쪽의 "할루시네이션 전파 대응"을 그대로 가져오고, 3-1의 원칙에 따라 순서를 붙였음.  
코드로 확인하는 스키마 검증과 근거 대조를 먼저, LLM을 쓰는 교차검증을 뒤에 둠.

| 순서 | 해결책 | 설명 |
|---|---|---|
| 1 | 스키마 검증 | 정해진 JSON, Pydantic 형식과 필수 필드를 만족하는지 확인 |
| 2 | 근거 대조 | DB, 문서, API, 검색 결과 같은 외부 근거와 대조 |
| 3 | 교차검증 | 다른 모델, 다른 프롬프트, 다른 에이전트로 검토해 일관성 확인 |
| 4 | 실패 시 체인 차단 | 다음 에이전트로 넘기지 않고 재시도하거나 사람 확인으로 올림 |

**주의**: 모델이 스스로 낸 확신도(confidence)만 믿지 않음.  
출처 유무, 검증 결과, 모델 간 일치를 함께 봄.  
하네스 공개 논문은 자기 검증의 효과가 모델이 틀리고도 확신하는 비율에 따라 달라진다고 설명함.  
확신도만 믿으면 안 되는 이유임.

**앞선 교재와 달라진 점**  
- 내용은 그대로 두고 검사의 순서를 붙였음. 코드 검사를 먼저 하는 것이 3-1의 원칙임.

### 4-1 MAS 실행 리스크 지도

### 4-2 비용 통제

비용은 나중에 확인할 일이 아니라 실행 중에 제한할 일임.

### 4-3 안정성 통제

한 곳의 실패가 전체로 번지지 않게 실행 단계에서 막음.

**쉬운 설명**

이 장치들은 대부분 기존 분산 시스템의 운영 패턴임. 틀린 내용은 아니며 에이전트에 그대로 적용됨.  
에이전트에서 특히 중요한 것은 연쇄 실패(한 곳의 오류가 줄줄이 번지는 일)임.  
OWASP 에이전트 보안 Top 10도 ASI08로 연쇄 실패를 따로 꼽음.

**장애 확산 막기**

| 장치 | 하는 일 |
|---|---|
| Circuit Breaker | 연속 실패하는 LLM API나 도구를 잠시 차단 |
| 리소스 격리 | 에이전트별 CPU, 메모리, 실행 환경 분리 |
| 성능 저하 모드 | 일부가 실패해도 핵심 기능만으로 제한된 답 제공 |
| Backpressure | 처리량을 넘는 요청은 대기, 제한, 거절 |

**지연 줄이기**

| 장치 | 하는 일 |
|---|---|
| 병렬 실행 | 서로 기다릴 필요 없는 작업을 동시에 |
| 계층적 타임아웃 | 도구, 단계, 에이전트, 워크플로우마다 따로 |
| 캐싱 | 같은 입력의 LLM 답, 검색, 도구 결과 재사용 |
| 스트리밍 | 중간 결과와 진행 상황을 먼저 보여 줌 |

Circuit Breaker는 집의 차단기처럼 계속 문제가 나는 곳을 잠시 끊는 장치임.  
(비유가 맞지 않는 점: 차단기는 사람이 올리지만, 소프트웨어 차단기는 일정 시간 뒤 자동으로 재시도할 수 있음.)  
Backpressure는 처리할 수 있는 양을 넘는 요청을 밀어 넣지 않고 대기시키거나 거절하는 방식임.

**에이전트에 적용하면**: LLM API가 연속 실패하면 다른 모델로 넘김(폴백).

모델 넘김과 도구 단위 차단을 함께 설계함.

**앞선 교재와 달라진 점**

- 에이전트 사례(모델 폴백, 도구 단위 차단)를 붙였음.

### 4-4 보안 1: 구조로 막기

위험한 능력 세 가지를 한 에이전트에 모두 주지 않음(Rule of Two).

**쉬운 설명**

프롬프트 인젝션(모델에게 몰래 나쁜 지시를 심는 공격)을 완벽히 막는 방법은 아직 없음.  
그래서 공격이 성공해도 큰 피해가 나지 않도록 구조를 먼저 짬.  
Meta의 Rule of Two는 한 세션에서 아래 A, B, C 중 두 가지까지만 허용하라고 함.  
셋이 모두 필요하면 자율 실행을 하지 않고 사람 승인 같은 확인을 붙임.  
- A: 믿을 수 없는 입력을 처리  
- B: 민감한 데이터나 시스템에 접근  
- C: 상태를 바꾸거나 외부로 전송

| 에이전트 예 | A | B | C | 판정 |
|---|---|---|---|---|
| 웹 검색 결과 요약 | O | X | X | 자율 실행 가능 |
| 받은 메일 요약만 | O | O | X | 자율 실행 가능 |
| 받은 메일 읽고 답장 발송 | O | O | O | 사람 승인 필요 |
| 사내 DB 보고서를 정해진 곳에 전송 | X | O | O | 자율 실행 가능 |

사적 데이터, 믿을 수 없는 콘텐츠, 외부 통신이 한곳에 모이면 데이터가 빠져나감.  
Simon Willison은 이를 치명적 삼중 조합(lethal trifecta)이라고 부름.  
Google DeepMind의 CaMeL은 믿을 수 있는 요청에서 실행 흐름을 먼저 정하고,  
믿을 수 없는 데이터가 그 흐름을 바꾸지 못하게 하는 설계를 보였음.

**앞선 교재와 달라진 점**  
- 앞선 교재에 없던 가장 중요한 보안 원칙임. 앞선 교재 145쪽은 이 구조 원칙 없이 개별 방어 기법만 나열했음.

### 4-5 보안 2: 프롬프트 인젝션 완화

필터는 우회되므로 보조로 두고, 막는 것이 아니라 피해를 줄이는 쪽으로 설계함.

**쉬운 설명**

앞선 교재 145쪽은 입력 필터링을 첫 항목으로 강조했음. 이번에는 순서를 바꿨음.  
필터는 알려진 문구만 잡고, 공격자는 그 필터에 맞춰 문구를 바꾸기 때문임.  
"The Attacker Moves Second" 연구는 공개된 방어 12개를 맞춤 공격으로 시험했고, 대부분 90% 넘게 뚫렸음.  
원래 논문에서는 거의 0%였던 방어들임.  
그래서 이 절은 "막는다"보다 "피해를 줄인다"는 표현을 씀.

| 순서 | 해결책 | 설명 |
|---|---|---|
| 1 | 위험 조합 분리 | 믿을 수 없는 입력, 민감 데이터, 외부 전송 중 두 가지까지만 허용(4-4) |
| 2 | 불신 데이터 표시 | 사용자 입력, 웹 문서, 외부 파일, 다른 에이전트 출력을 지시가 아닌 데이터로 다룸 |
| 3 | 샌드박스 | 공격이 성공해도 피해 범위가 좁도록 실행 공간 격리 |
| 4 | 역할 분리 | 공통 지침과 사용자 입력을 나눠 넣어 무시할 가능성을 낮춤(보장 아님) |
| 5 | 입력 필터링(보조) | 알려진 공격 문구를 걸러 냄. 우회될 수 있어 단독으로 쓰지 않음 |

**필터만으로 안 되는 이유**  
- 공개 방어 12개 대부분이 맞춤 공격에 90% 넘게 뚫림(2025-10)  
- NIST 레드팀 경연: 대상 모델 13종 모두에서 공격 성공(2026-03)  
- 여러 겹 방어 뒤에도 약 1% 성공이 남음(Anthropic, 2025-11)

**앞선 교재와 달라진 점**  
- 입력 필터링을 첫 항목에서 맨 아래 "보조"로 내렸음. 필터는 알려진 공격만 거르고 우회될 수 있기 때문임.  
- 역할 분리를 "강제한다"에서 "가능성을 낮춘다"로 고쳤음. LLM은 지시가 어디서 왔는지 확실히 구분하지 못함.  
- KISA 안내서(본문 54쪽)와 OWASP LLM01은 일곱 가지 대응을 함께 쓰라고 권함.  
  역할 분리(모델 동작 제한), 불신 데이터 표시(외부 콘텐츠 분리), 입력 필터링이 그 안에 있고,  
  나머지인 출력 형식 검증, 최소 권한, 고위험 작업 승인, 공격 시험은 3-4와 4-6에서 다룸.

### 4-6 보안 3: 데이터와 권한

허용 여부는 LLM이 아니라 연결된 시스템이 검사함.

**쉬운 설명**

앞선 교재 145쪽의 데이터 유출, 권한 오남용 대응은 국내외 권고와 잘 맞아 대부분 그대로 가져왔음.  
새로 넣은 것은 "연결 시스템에서 검사"임.  
KISA 안내서는 LLM에 의존해 허용 여부를 정하지 말고,  
데이터베이스 계정 권한처럼 연결된 시스템에서 권한을 구현하라고 권함.

**데이터 유출 대응**

| 장치 | 하는 일 |
|---|---|
| DLP 필터 | 출력과 외부 전송에서 개인정보, 계좌, 카드 번호 탐지 |
| 민감 정보 마스킹 | 탐지된 값을 가리거나 지움 |
| 네트워크 허용 목록 | 접근할 수 있는 API, 도메인만 허용 |
| 외부 전송 감사 로그 | 누가, 무엇을, 어디로, 어떤 요청으로 보냈는지 |

**권한 오남용 대응**

| 장치 | 하는 일 |
|---|---|
| 최소 권한 | 에이전트마다 필요한 권한만 |
| 도구 허용 목록 | 허용되지 않은 도구 호출 차단 |
| 연결 시스템에서 검사 | 권한 판단을 LLM이 아닌 연결 시스템이 함 |
| 고위험 작업 사람 승인 | 삭제, 결제, 외부 전송은 승인 뒤 실행 |

DLP(Data Loss Prevention)는 개인정보 같은 민감한 값이 밖으로 새지 않도록 탐지하고 막는 기술임.

**처리 흐름**: 사용자 입력 → 에이전트 → 고위험 작업 감지 → 권한 검사(코드) → 사람 승인 → 실행 또는 거부.  
이 흐름에서 권한 검사는 코드가 맡고, 모델에게 묻지 않음.

**앞선 교재와 달라진 점**  
- "연결 시스템에서 검사"를 새로 더했음.  
- 앞선 교재의 "시간과 작업 기준 권한 제한"은 슬라이드 표에서 빼고 이 상세 교재에만 남겼음.  
  시간과 작업을 기준으로 권한을 좁히는 일도 최소 권한 원칙의 한 방법임.

### 4-7 MAS만의 위험

다른 에이전트가 보낸 메시지와 공유 메모리도 믿을 수 없는 입력으로 다룸.

**쉬운 설명**

OWASP 에이전트 보안 Top 10에는 앞선 교재 9대 리스크에 없는 MAS 위험이 있음.  
그중 에이전트 간 통신(ASI07)과 메모리 오염(ASI06)이 MAS에서 특히 중요함.  
에이전트 A의 출력이 에이전트 B의 입력이 되는 순간, 그 출력은 B 입장에서 바깥에서 온 데이터임.  
웹 문서처럼 지시가 아닌 데이터로 다뤄야 함.  
OWASP는 메모리에 저장하기 전에 내용을 검사하고, 에이전트가 만든 출력을 믿을 수 있는 메모리에 자동으로 다시 넣지 말라고 권함.

| OWASP 번호 | 위험 | 무슨 일이 생기나 | 대응 |
|---|---|---|---|
| ASI07 | 에이전트 간 통신 | 가짜 메시지나 숨은 지시가 다른 에이전트로 전달됨 | 에이전트마다 신원 인증, 메시지 서명과 변조 확인, 허용한 프로토콜 버전만 사용 |
| ASI06 | 메모리와 컨텍스트 오염 | 공유 메모리에 나쁜 내용이 저장되어 계속 쓰임 | 저장 전 내용 검사, 세션별 메모리 분리와 출처 기록, 검증 안 된 기억은 만료 |
| ASI08 | 연쇄 실패 | 한 에이전트의 오류가 줄줄이 번짐 | 검증 실패 시 체인 차단(3-4), Circuit Breaker(4-3) |

국내 업계 인터뷰에서도 에이전트끼리 연결되면 한 곳의 사고가 협력사까지 번질 수 있다는 지적이 나옴.

**앞선 교재와 달라진 점**  
- 앞선 교재 145쪽에는 MAS 특유의 경로가 없었음. 다른 에이전트의 출력도 오염될 수 있다는 점을 더했음.

### 5-1 트레이스

에이전트가 무엇을 보고 무엇을 했는지 전부 남겨야 원인을 찾을 수 있음.

**쉬운 설명**

트레이스는 한 번의 실행에서 일어난 모든 일, 곧 출력, 도구 호출, 추론, 중간 결과를 담은 기록임.  
LangChain은 모델 내부는 들여다볼 수 없지만 입력과 출력은 볼 수 있으니 트레이스로 실패 유형을 찾는다고 설명함.  
하네스 개선의 출발점임.

### 5-2 평가셋으로 재기

말이 아니라 결과(환경의 최종 상태)로 채점하고, 하네스와 모델을 함께 평가함.

**쉬운 설명**

Anthropic은 에이전트 평가를 과제(task), 시도(trial), 채점기(grader)로 나눔.  
채점기는 코드, 모델, 사람이 될 수 있고 하나의 과제에 여러 채점기를 붙일 수 있음.  
흐름은 과제, 여러 번 시도, 채점기 세 종류, 점수 순서임.  
평가셋은 이런 과제와 정답 기준을 모아 둔 묶음임.

**결과로 채점하는 예**  
- 항공권 예약 에이전트가 "예약했습니다"라고 말해도  
- 실제 예약 DB에 기록이 있는지로 채점함

에이전트가 하는 말이 아니라 환경의 최종 상태, 곧 결과로 채점함.  
에이전트를 평가한다는 것은 하네스와 모델을 함께 평가하는 것임.  
그래서 하네스를 바꿀 때마다 같은 평가셋으로 다시 잼.

| 지표 | 뜻 | 쓰임 |
|---|---|---|
| pass@k | k번 중 한 번이라도 성공 | 한 번만 맞으면 되는 일 |
| pass^k | k번 모두 성공 | 매번 맞아야 하는 운영 업무 |

pass^k는 k가 커질수록 떨어짐. 운영 업무에서는 이 일관성이 중요함.

### 5-3 조향 루프

같은 실수가 다시 나지 않도록, 실수할 때마다 장치를 하나 더함.

**쉬운 설명**

Mitchell Hashimoto는 에이전트가 실수할 때마다 그 실수가 다시 일어나지 않게 해결책을 만드는 일을  
하네스 엔지니어링이라고 불렀음. AGENTS.md를 고치거나, 에이전트가 스스로 확인할 도구를 만드는 식임.  
OpenAI Codex 팀도 실패했을 때 "더 열심히 해 봐"가 아니라  
"어떤 능력이 빠졌고, 그걸 에이전트가 알아보고 지키게 하려면 무엇이 필요한가"를 물었다고 함.  
Böckeler는 이를 조향 루프(steering loop)라고 부름. 사람은 직접 일하는 대신 하네스를 고쳐 에이전트를 조종함.

**루프 4단계**  
1. 실패 발견(트레이스, 평가)  
2. 원인 분류  
3. 장치 추가  
4. 평가로 확인한 뒤 다시 1단계로

| 원인 | 추가할 장치 | 층 |
|---|---|---|
| 필요한 정보를 몰랐음 | 지침 한 줄, 문서 연결 | 1층 |
| 결과를 확인하지 않았음 | 테스트, 린터, 스키마 검증 | 2층 |
| 위험한 행동을 했음 | 권한 축소, 사람 승인 | 3층 |
| 원인을 모르겠음 | 트레이스 항목 추가 | 4층 |

원인을 모르면 먼저 4층 장치(트레이스)를 보강해서 다음 실패에서는 원인이 보이게 함.

### 5-4 엔트로피 관리

에이전트가 만든 결과물은 조금씩 어긋나므로 정기적으로 정리함.

**쉬운 설명**

에이전트가 코드를 많이 만들수록 일관성이 조금씩 무너짐(엔트로피가 늘어난다고 표현함).  
에이전트는 이미 있는 패턴을 따라 하기 때문에 나쁜 패턴도 빠르게 퍼짐.  
OpenAI Codex 팀은 "황금 원칙"을 저장소에 적어 두고,  
정기적으로 백그라운드 작업이 위반을 찾아 작은 수정 요청을 올리게 했음.  
이를 가비지 컬렉션(쓰지 않는 메모리를 주기적으로 치우는 일)에 빗댐.  
사람의 취향을 한 번 적어 두면 모든 코드에 계속 적용된다는 점이 핵심임.

| 단계 | 내용 |
|---|---|
| 문제 | 에이전트는 기존 코드의 패턴을 따라 함. 나쁜 패턴도 그대로 퍼짐 |
| 황금 원칙 | 공용 도구를 쓰고 직접 만들지 않음. 데이터 모양을 추측하지 않고 경계에서 검증 |
| 정기 정리 작업 | 백그라운드 에이전트가 원칙 위반을 찾음. 작은 수정 요청을 올림. 대부분 1분 안에 검토 |

기술 부채는 이자가 높은 빚과 같음. 조금씩 자주 갚는 편이 낫다는 비유가 이 절의 핵심 메시지임.  
(비유가 맞지 않는 점: 기술 부채의 "이자"는 돈이 아니라 이후 작업이 느려지는 비용임.)

### 5-5 하네스 다이어트

모델이 바뀌면 장치를 하나씩 빼 보고, 효과 없는 것은 지움.

**쉬운 설명**

하네스의 장치 하나하나는 "모델이 혼자 못 하는 것"에 대한 가정임. 모델이 좋아지면 그 가정이 틀려짐.  
Anthropic은 새 모델이 나오면 하네스를 다시 살펴, 더는 성능을 받치지 않는 장치는 걷어내고  
새로 가능해진 장치를 더하라고 권함.

**사례**  
- 이전 모델은 컨텍스트 한계가 가까워지면 서둘러 끝냄  
- 그래서 컨텍스트 리셋 장치를 넣음  
- 새 모델에서 버릇이 사라져 장치를 뺌

**절차**  
1. 장치 목록 작성  
2. 하나씩 끄고 평가셋 실행  
3. 점수 차이가 없으면 제거

**연구 동향**: Meta-Harness 연구는 이전 하네스들의 코드, 점수, 실행 기록을 보고 하네스를 자동으로 고쳐 나감.  
논문은 기존 방식보다 7.7점 높고 컨텍스트 토큰은 4분의 1이라고 보고함.  
하네스 최적화도 자동화되는 흐름임.

장치를 뺄 때는 꼭 평가셋(5-2)으로 점수 차이를 확인함. 감으로 지우면 안 됨.

### 6-1 적용 6단계

### 6-2 첫날부터 넣을 최소 하네스

### 6-5 실습 안내

하네스 없는 문서 Q&A 에이전트에 장치를 하나씩 붙이고 전후를 비교함.

**쉬운 설명**

실습은 6-1의 적용 단계를 작게 따라 해 보는 것임.  
장치 하나를 붙일 때마다 같은 평가 질문으로 다시 재어 변화를 눈으로 확인함.  
LangGraph의 반복 상한, 중단 후 승인 대기, 체크포인터 같은 기능을 씀.  
구체 API는 실습 가이드에서 최신 문서 기준으로 안내함. 이 문서에는 LangGraph 코드를 싣지 않음.

| 단계 | 붙이는 장치 | 층 | 확인 방법 |
|---|---|---|---|
| 0 | 하네스 없는 기본 에이전트 | 없음 | 평가 질문 5개의 점수, 토큰, 시간 기록 |
| 1 | 반복 상한과 예산 상한 | 3층 | 무한 반복을 부르는 질문에서 정해진 횟수에 멈추고 부분 결과 반환 |
| 2 | 짧은 지침과 도구 설명 정리 | 1층 | 같은 질문에서 잘못된 도구 호출 횟수 감소 |
| 3 | 답변 스키마 검증과 근거 대조 | 2층 | 근거 없는 답변이 다음 단계로 넘어가지 않음 |
| 4 | 외부 전송 도구에 사람 승인 | 3층 | 승인 전에는 실행되지 않고 대기 |
| 5 | 트레이스 기록과 평가 재실행 | 4층 | 0단계 대비 점수, 토큰, 실패 유형 비교표 |

**단계마다 무엇을 관찰하나**  
- 0단계: 장치가 하나도 없을 때의 기준선을 만듦.  
  이후 모든 단계의 점수, 토큰, 시간을 이 숫자와 비교하므로 가장 먼저 정확히 기록함.  
- 1단계: 일부러 끝나지 않을 질문을 던져 에이전트가 정해진 횟수에서 멈추는지 봄.  
  멈출 때 그때까지의 부분 결과와 멈춘 사유가 함께 돌아오는지도 확인함.  
- 2단계: 같은 질문을 다시 돌려 잘못된 도구를 부르는 횟수가 줄었는지 셈.  
  지침과 도구 설명을 고치기 전후의 차이만 보도록 다른 조건은 그대로 둠.  
- 3단계: 근거가 없는 답이 만들어졌을 때 검증 관문에서 걸러져 다음 단계로 넘어가지 않는지 봄.  
  걸러진 답이 재시도되거나 사람 확인으로 올라가는 길도 함께 확인함.  
- 4단계: 외부 전송 도구를 부르려 할 때 승인 전에는 실행되지 않고 멈춰 기다리는지 봄.  
  승인하면 이어서 실행되고, 거부하면 실행되지 않는지도 확인함.  
- 5단계: 모든 단계가 기록된 트레이스를 열어 실패 유형을 분류하고, 같은 평가 질문 5개를 다시 돌려 0단계와 비교함.  
  점수만 보지 말고 토큰과 실패 유형이 어떻게 달라졌는지 함께 봄.

**준비물**: 팀 저장소 RAG 예제(`teacher/rag`), LangGraph, 평가 질문 5개  
**결과물**: 단계별 점수, 토큰, 실패 유형 비교표

### 6-6 정리와 점검표

**쉬운 설명**

점검표는 4층 지도를 그대로 따름. "아니오"가 나온 문항이 다음에 붙일 장치임.

| 층 | 점검 문항 |
|---|---|
| 1층 | 지침 파일이 짧은 목차로 되어 있나 |
| 1층 | 도구가 좁은 기능과 분명한 오류 응답을 갖나 |
| 1층 | 컨텍스트 길이를 관리하나 |
| 1층 | 작업 상태가 바깥에 저장되나 |
| 2층 | 결과를 코드 검사로 먼저 확인하나 |

## 용어사전

| 용어 | 쉬운 풀이 |
|---|---|
| Agent Harness(하네스) | 에이전트에서 모델(LLM)을 뺀 모든 것. 지침, 도구, 검증, 권한, 기록 등 |
| Backpressure | 처리할 수 있는 양을 넘는 요청을 밀어 넣지 않고 대기시키거나 거절하는 방식 |
| Circuit Breaker | 계속 실패하는 대상(LLM API, 도구)을 잠시 끊어 문제가 번지지 않게 하는 장치 |
| CI | 코드를 올릴 때마다 정해진 검사를 자동으로 돌리는 방식 |
| context rot | 컨텍스트가 길어질수록 모델이 정보를 정확히 떠올리지 못하게 되는 현상 |
| DLP | 개인정보 같은 민감한 값이 밖으로 새지 않도록 탐지하고 막는 기술 |
| Kill-switch | 이상이 생겼을 때 전체 실행을 즉시 멈추는 비상 스위치 |
| pass@k, pass^k | k번 시도 중 한 번이라도 성공하면 맞는 지표와, k번 모두 성공해야 맞는 지표 |
| Rule of Two | 믿을 수 없는 입력, 민감 데이터 접근, 상태 변경이나 외부 전송 중 한 에이전트에 두 가지까지만 주는 원칙 |
| 가이드(feedforward) | 에이전트가 행동하기 전에 방향을 알려 주는 장치 |
| 가드레일 | 사고가 나지 않도록 선을 넘지 못하게 막는 장치 |
| 린터 | 코드가 정해진 규칙을 지켰는지 자동으로 검사하는 도구 |
| 미들웨어 | 모델과 도구 사이에서 정해진 시점에 끼어들어 검사하는 코드 |
| 샌드박스 | 문제가 생겨도 바깥에 피해가 번지지 않게 격리한 실행 공간 |
| 서브에이전트 | 메인 에이전트가 일부 조사를 맡기는 보조 에이전트 |
| 센서(feedback) | 에이전트가 행동한 뒤 결과를 확인하는 장치 |
| 스키마 | 데이터가 갖춰야 할 모양(필드 이름과 형식)을 정해 둔 틀 |
| 스프린트 계약 | 코드를 쓰기 전에 생성자와 평가자가 "다 됨"의 모습을 먼저 합의하는 일 |
| 조향 루프 | 실수를 보고 장치를 하나 더하는 일을 되풀이하며 하네스를 고쳐 가는 순환 |
| 컨텍스트 | 모델이 한 번에 읽는 정보 전체(지시문, 검색 결과, 이력, 도구 결과) |
| 컴팩션 | 컨텍스트가 한계에 가까워질 때 대화를 요약해 이어 가는 기법 |
| 토큰 | 모델이 글을 읽고 쓰는 단위. 비용과 지연이 토큰 수에 비례함 |
| 트레이스 | 한 번의 실행에서 일어난 모든 일의 기록 |
| 평가셋 | 하네스와 모델을 채점하기 위해 모아 둔 과제와 정답 기준의 묶음 |
| 프롬프트 인젝션 | 입력이나 외부 문서에 나쁜 지시를 심어 모델의 행동을 바꾸려는 공격 |
| 할루시네이션 | 모델이 사실이 아닌 내용을 그럴듯하게 만들어 내는 현상 |
