# GraphRAG Agentic 검색 PPT 검토 의견

검토일: 2026-10-24  
대상: `graphrag-agentic-search.pptx`의 1 ~ 11장

전체 흐름에서 검색 모드를 선택하는 일과 검색 결과를 보고 행동을 바꾸는 일을 구분한 점은 이해하기 좋습니다.  
O4와 7단계 리랭킹의 목적을 나누고, 장애 시 대체 경로를 설명한 구성도 유지할 만합니다.  
다만 교육 자료로 사용하기 전에 종료 판단과 재검색 제한의 충돌을 먼저 정리하는 편이 좋겠습니다.

아래 의견은 실제 PPTX 본문과 발표자 노트, LibreOffice로 렌더링한 11장, 같은 이름의 상세 설계를 대조한 결과입니다.  
서비스 동작이나 슬라이드에 기재된 성능 실측을 재현한 검토는 아닙니다. 원본 PPTX는 수정하지 않았습니다.  
검색 설계는 지식니, 실행 흐름은 플로니가 검토했으며, 두 전문 검토에는 `gpt-5.6-sol`을 사용했습니다.

## 1. 우선 수정: 한 문장에 두 단어가 없다는 이유로 검색을 종료하면 안 됩니다

**위치: 4장 `NO_COOCCUR`, 5장 해당 신호의 행동**

4장은 핵심 명사 두 개가 한 문장에 함께 나온 근거가 없으면 “답이 없는 질문”으로 판단하고, 5장은 검색을 종료합니다.  
하지만 서로 다른 문장이나 문서에 있는 관계를 연결해야 답할 수 있는 질문도 있습니다.  
예를 들어 한 문서에는 카드와 혜택의 관계가, 다른 문서에는 그 혜택의 적용 조건이 있을 수 있습니다.  
이 경우 한 문장 안의 단어 공존 여부로 종료하면 그래프를 사용하는 이유와 충돌합니다.

`NO_COOCCUR`의 뜻을 “직접 함께 언급된 근거를 찾지 못함”으로 바꾸고, 관계 탐색이나 질문 분해를 검토하는 신호로 쓰기를 권합니다.  
종료할 때도 “답이 없음”보다 “현재 확보한 근거로는 답을 확인할 수 없음”으로 표현하는 것이 정확합니다.  
발표자 노트의 Q18, Q20 사례만으로 이 규칙을 모든 질문에 적용하기는 어렵습니다.

## 2. 우선 수정: 재검색 행동과 금지 규칙의 우선순위를 정해야 합니다

**위치: 5장 행동표와 오른쪽 금지 규칙**

다음 두 상황에서는 같은 화면의 규칙이 서로 다른 행동을 요구합니다. 상세 설계 2-3절에도 같은 문제가 남아 있습니다.

- `ID_MISMATCH`는 “필터 강화 → 같은 모드”를 요구하지만, 같은 모드와 질의의 재검색은 금지합니다.  
  필터만 바뀌는 경우에도 복구 검색을 허용하는지 명시해야 합니다. 검색 이력의 비교 기준에 필터를 포함하고,  
  필터 수정 재검색은 1회만 허용하는 방식으로 정리할 수 있습니다.
- local에서 `SCATTERED`가 발생해 global로 바꾼 뒤, `NO_REPORTS`가 나오면 행동표는 local 복귀를 요구합니다.  
  그러나 모드 전환은 1회이며 반대 방향은 금지되어 있습니다. 처음부터 global로 시작했을 때만 local 전환을 허용하고,  
  이미 전환했다면 기존 근거로 수집을 종료하는 등 두 경우를 나누어 설명해야 합니다.

global에서 `ID_MISMATCH`가 발생하면 “global은 요청당 1번” 규칙도 함께 걸립니다.  
LLM이 행동을 고르게 하기 전에 허용 가능한 행동과 제한에 도달했을 때의 종료 경로를 확정하는 편이 좋겠습니다.

## 3. 우선 수정: Global의 통과 기준과 주제별 근거 보존 기준을 맞춰야 합니다

**위치: 4장 `PASS(global)`, 8장 `topic_ids`, 11장 원문 8개 선정**

4장은 Follow-up 원문이 전체에서 1개만 있어도 통과할 수 있지만, 8장은 질문을 최대 5개 만들고,  
11장은 `topic_ids`마다 원문을 최소 1개 보존한다고 설명합니다. 한 주제만 근거를 찾고 나머지는 찾지 못한 경우,  
전체 질문을 통과시켜도 되는지가 불분명합니다.

또한 8장은 `topic_ids`를 “보고서 id”라고 설명하면서 보고서 최대 12개를 주제 1 ~ 5개로 묶습니다.  
보고서별 보존인지 묶인 주제별 보존인지에 따라 11장의 원문 최대 8개와 양립할 수 있는 조건이 달라집니다.  
여러 보고서가 같은 원문을 공유할 수도 있으므로 항상 모순이라고 단정할 수는 없지만, 현재 설명만으로 보존을 보장하기는 어렵습니다.

보고서 ID와 주제 그룹 ID를 구분하고, “답변에 포함할 주제마다 원문 근거가 있어야 함”을 통과 기준에 반영하기를 권합니다.  
근거를 확보하지 못한 주제는 답변 범위에서 제외하거나 미확인으로 표시하면 됩니다.  
7단계에서 근거를 줄인 뒤에도 이 기준이 유지되는지 8단계에서 다시 확인하도록 설명을 보완해 주세요.

## 4. 수정 권고: 보고서 관련도 점수의 출처를 밝혀야 합니다

**위치: 4장 관련도 0.35와 0.25, 8장 G1 보고서 선택**

G1은 LLM이 제목을 보고 보고서를 선택한다고 설명하지만, 채점표는 숫자 형태의 관련도를 사용합니다.  
이 점수가 질문과 보고서의 임베딩 유사도인지, 리랭커 점수인지, LLM이 별도로 출력하는 점수인지 설명이 없습니다.  
상세 설계에서도 점수 산정 방법을 확인하기 어렵습니다.

점수를 만드는 방법, 비교 대상, 여러 보고서 점수를 합치는 기준을 명시해 주세요.  
예를 들어 “질문과 보고서 요약의 임베딩 코사인 유사도 중 최댓값”처럼 정의하면 독자가 구현 기준을 이해할 수 있습니다.  
이는 정의 방식의 예시이며, 실제 방법을 정한 뒤 임계값을 평가셋으로 조정해야 합니다.  
임계값을 가정값으로 표시한 현재 문구는 유지하는 것이 좋습니다.

## 5. 수정 권고: 병렬 검색을 도식에서도 병렬로 보여 주세요

**위치: 6장 검색엔진 검색(O) 흐름도**

그림은 `O1 벡터 검색 → O2 BM25 검색 → O3 RRF → O4 리랭킹`으로 연결되어 있습니다.  
반면 바로 아래 설명과 상세 설계는 O1과 O2가 병렬이라고 명시합니다. 그림만 보면 벡터 검색 결과를 BM25에 넘기는 구조로 읽힙니다.

동일한 질의에서 O1과 O2로 갈라지고, 두 결과가 O3로 합쳐지는 형태로 바꾸는 것이 좋습니다.  
두 갈래에 각각 “최대 25개”, 합쳐진 후보에 중복 제거와 상위 25개 선정, O4 출력에 “최대 6개”를 표시하면 더 명확합니다.

## 6. 수정 권고: 상세 설계에서 빠진 분기 조건과 신호 이름을 맞춰 주세요

**위치: 4장 `SCATTERED`, 5장 `LOW_COVERAGE`와 `OFF_TOPIC`**

- 상세 설계 2-2절의 `SCATTERED`는 출처 분산과 함께 “포함률 0.6 미만”을 요구합니다.  
  4장은 포함률 조건을 생략해, 이미 충분한 근거가 있어도 문서가 여러 개라는 이유로 global 전환 신호가 생길 수 있습니다.
- 상세 설계 2-3절의 `LOW_COVERAGE` 분해 행동은 “local, 복합 질문”에 해당합니다.  
  5장은 복합 질문 조건을 생략해 단순 질문까지 분해하는 것으로 읽힙니다. 단순 질문일 때의 행동도 구분해 주세요.
- 4장과 11장은 `OFF_TOPIC_REPORTS`를 사용하지만 5장은 `OFF_TOPIC`으로 줄여 씁니다.  
  코드와 대응하는 신호라면 이름을 통일하는 편이 좋습니다.

교육용으로 내용을 줄이더라도 실제 분기를 바꾸는 조건은 남겨야 합니다.

## 7. 수정 권고: 이 자료의 Global 검색이 자체 구성임을 밝혀 주세요

**위치: 3장 검색 모드, 6장 서브 워크플로우, 8장 Global 검색**

이 자료의 Global은 제목으로 보고서를 고르고, 추가 질문을 만든 뒤 Local 검색으로 사실을 확인하는 구조입니다.  
Microsoft GraphRAG 공식 설명의 Global Search는 커뮤니티 보고서를 map-reduce 방식으로 처리합니다.  
보고서에서 추가 질문을 만들어 Local 검색으로 이어가는 접근은 공식 DRIFT 설명과 닮은 부분이 있습니다.  
근거: [공식 검색 방식 개요][graphrag-overview], [공식 DRIFT 설명][graphrag-drift].

현재 설계를 공식 구현에 맞춰 바꿀 필요는 없습니다.  
“이 실습의 local/global은 자체 검색 모드이며, Global은 보고서 선택과 Follow-up Local 검색을 결합한 구성”이라고  
처음 소개하는 곳에 명시하면 충분합니다. DRIFT와 완전히 같은 구현이라고 표현하는 것도 피하는 편이 좋습니다.

## 8. 수정 권고: 보고서 개수 제한과 토큰 예산 제한을 구분해 주세요

**위치: 8장 “고른 12개의 본문은 약 11,700 토큰으로 컨텍스트 예산 12,000 안”**

특정 보고서 12개의 측정값이 예산 안에 들어간다는 사실만으로, 어떤 보고서 12개를 골라도 예산을 지킨다고 볼 수는 없습니다.  
또한 12,000이 보고서 본문만의 예산인지, 질문과 지시문을 포함한 입력 전체의 예산인지 구분되어 있지 않습니다.

“측정한 12개 보고서는 약 11,700토큰”이라고 측정 범위를 한정하고, 선택 후 실제 토큰 수를 확인한다고 설명해 주세요.  
예산을 넘으면 보고서를 줄이거나 요약하는 순서도 한 줄로 덧붙이면 좋습니다.  
이는 시간 예산을 추가하자는 의견이 아니라, 슬라이드에 이미 제시한 컨텍스트 예산을 지키기 위한 보완입니다.

## 9. 수정 권고: 측정 결과와 설계상 기대 효과를 구분해 주세요

**위치: 8장 발표자 노트, 10장 선택 이유**

“상담 보고서 12개를 벡터 5개로는 못 담음(재현율 42%)”에는 분모와 실제 검색 결과의 정의가 필요합니다.  
12개가 모두 해당 질문의 관련 보고서라고 가정하면, 5개만 고르는 방식의 보고서 재현율 상한은 약 41.7%입니다.  
하지만 이 계산만으로 실제 검색에서 관련 보고서 5개를 찾았다고 확인되거나, 답변 품질이 42%라고 해석되지는 않습니다.  
실측값이라면 관련 보고서 정답 목록과 검색 결과를 연결하고, 단순 계산이라면 “보고서 포함 상한 5/12”로 표현해 주세요.

같은 표의 “Cypher 1번 → 세대 필터 누락 위험 없음”도 보장 범위가 넓습니다.  
호출을 합쳐도 쿼리 안에서 필터를 빠뜨릴 수 있으므로 “세대 필터를 한 쿼리에서 일관되게 적용하기 쉬움”이 적절합니다.

“로컬 모델은 병렬이 직렬로 무너짐”은 CPU, 모델, 실행 방식에 따른 판단입니다.  
측정 로그가 있다면 환경과 결과를 연결하고, 없다면 “현재 CPU 실습 환경에서 처리 병목이 예상되어 제외”처럼 한정해 주세요.  
검토 과정에서 이 성능 실측을 재현하지 않았으므로, 기존 측정이 틀렸다는 뜻은 아닙니다.

## 10. 배포 전 확인: 상세 보기 링크의 접근 조건을 점검해 주세요

**위치: 1 ~ 11장의 `상세 보기` 링크**

모든 링크는 같은 GitHub `main` 브랜치의 상세 문서에 장별 앵커를 붙인 형태입니다.  
검토 시 인증하지 않은 요청에서 공통 문서 URL이 HTTP 404를 반환했습니다.  
비공개 저장소이거나 아직 해당 브랜치에 반영되지 않은 경우도 있으므로, 이 결과만으로 문서가 없다고 단정하지는 않습니다.

수강생 계정으로 문서와 각 절에 접근할 수 있는지 확인하고, 접근 권한이 필요한 자료라면 그 조건을 안내해 주세요.  
배포본과 상세 설계가 나중에 달라지는 것을 막으려면 검토한 버전의 커밋 링크를 쓰는 방법도 있습니다.
