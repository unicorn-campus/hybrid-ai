## 2. collection 고르기와 읽기 확인

### 개념 설명
벡터DB에서 청크를 빠짐없이, 겹치지 않게 읽었는지 확인하는 단계임.  
여기서 빠지거나 겹치면 뒤의 표본과 시험 숫자가 모두 틀어지므로 건수를 먼저 맞춤.  
읽기만 했고 벡터DB에는 아무것도 쓰지 않았음.  

| 저장 폴더 | collection | 건수(count) | 읽은 건수 | ID 겹침 | 빈 본문 | 빈 메타데이터 | 판정 |
|---|---|---|---|---|---|---|---|
| `hands-on/solutions/rag/indexing/data/chroma` | `card_docs` | 260 | 260 | 0 | 0 | 0 | 통과 |

열 뜻  
- 건수(count): 벡터DB가 알려 준 collection의 청크 수(`collection.count()`)  
- 읽은 건수: `collection.get()`으로 실제로 꺼낸 청크 수. 건수와 같아야 함  
- ID 겹침: 같은 청크 ID가 두 번 나온 수  
- 빈 본문, 빈 메타데이터: 본문 글이나 딸린 정보(메타데이터)가 비어 있는 청크 수  
- 청크: 문서를 검색하기 좋게 자른 조각. 메타데이터는 청크에 딸린 정보(문서 종류, 쪽 번호, 카드 ID 등)  

참고: 같은 이름의 collection이 `teacher/rag/indexing/data/chroma`(260건, 강사용 사본)와  
`hands-on/solutions/rag/indexing/data-limit/chroma`(64건, 줄인 표본)에도 있음. 추천은 위 표의 폴더임.  

## 3. 청크 구조: 본문 칸과 문서 종류

### 개념 설명
청크의 어느 칸이 정제된 본문인지, 어느 메타데이터 칸이 문서 종류를 가리키는지 정함.  
문서 종류마다 스키마를 따로 만들기 때문에, 이번에 설계할 문서 종류를 여기서 고름.  

| 문서 종류(doc_type 값) | 청크 수 | 원본 | 본문 길이(최소 / 중간 / 최대, 글자) | 딸린 메타데이터 | 설계 추천 |
|---|---|---|---|---|---|
| regulation | 15 | 약관 PDF 1개 | 197 / 690 / 1,314 | page | 설계함 |
| benefit_guide | 197 | 카드 혜택 안내 PDF 1개 | 321 / 661 / 1,513 | page, card_id(195건, 64종), card_name(195건, 64종) | 설계함 |
| consult_log | 48 | 상담 이력 txt 6개(고객군마다 8건) | 729 / 824 / 925 | record_id(48종), member_pseudo_id(12종), consult_date(34종), channel(3종) | 설계함 |

열 뜻  
- 문서 종류: 메타데이터 `doc_type` 칸의 값. regulation은 약관, benefit_guide는 카드 혜택 안내, consult_log는 상담 기록  
- 본문 길이: 청크 본문의 글자 수. 중간은 길이순으로 줄 세웠을 때 가운데 값  
- 딸린 메타데이터: 그 문서 종류의 청크에만 있는 칸. 괄호는 값이 있는 청크 수와 값의 종류 수  
- 공통 메타데이터: 모든 청크에 `doc_type`, `source`(원본 파일 이름), `access_level`(공개 등급)이 있음  
- member_pseudo_id: 회원 번호를 알아볼 수 없게 바꾼 가명 ID  

분석 결과와 제안  
- 본문 칸: `documents` 값을 그대로 씀. 검색용 별칭을 덧붙인 흔적은 없음(별칭 치환은 BM25 색인 쪽에서만 함).  
  다만 카드 혜택 청크의 첫 줄에는 인덱서가 붙인 머리줄 `[카드: 카드 이름 (카드 ID)]`가 있음.  
  메타데이터에 원래 본문 칸은 따로 없음  
- 문서 종류 칸: `doc_type`  
- 설계할 문서 종류: 3종 모두 추천함. 온톨로지 규칙은 원천이 여럿일 때 쓰임새가 드러나고, 평가 질문 Q25가 3종을 모두 이음  
- 눈에 띈 점: 카드 혜택 청크 197건 중 2건은 card_id가 없음(표지나 안내 쪽으로 보임. 3단계에서 확인함)

## 5. 원천 목록 표

### 개념 설명
원천은 데이터가 나온 곳임. 이번에 설계하는 문서 3종 말고, 문서와 이어질 다른 원천이 무엇인지 적은 표임.  
여기 적힌 라벨과 키 속성만 공통 개념 층에 쓸 수 있고, 명세에 없는 것은 AI가 지어내지 않음.  
AI는 정형 DB에 접속하지 않고 아래 명세 파일만 읽음.  

| 원천 이름 | 종류 | 명세 파일 | 라벨(한글 이름) | 키 속성 |
|---|---|---|---|---|
| 정형 DB(cardlab) | 정형 DB(PostgreSQL) | `hands-on/solutions/graphrag-ontology/schema/rdb/graph_schema.json`, `…/schema/rdb/output/structure.json` | Member(회원) | member_id |
| | | | Card(카드) | card_id |
| | | | Product(상품) | product_id |
| | | | ProductAnnualFee(상품연회비) | product_id와 brand |
| | | | Merchant(가맹점) | merchant_id |
| | | | CardTxn(카드거래) | txn_id |
| | | | Delinquency(연체) | member_id와 base_month |

열 뜻  
- 종류: 문서인지 정형 DB(표로 된 데이터베이스)인지  
- 명세 파일: 그 원천의 구조를 적은 파일. `design-kg-schema-rdb.md` 프롬프트의 승인된 산출물임  
- 라벨: 그래프에서 같은 종류의 점(노드)에 붙이는 이름. 괄호는 명세의 description에 적힌 한글 이름  
- 키 속성: 그 라벨의 대상 하나를 가려내는 값(명세의 UNIQUENESS 제약에서 읽음)  

명세에서 읽은 것과 읽지 못한 것  
- 읽은 것: 라벨 7개, 관계 6개(HAS_CARD, APPLIES_FEE, MADE_TXN, AT_MERCHANT, HAS_DELINQUENCY, HAS_ANNUAL_FEE), 테이블 8개의 컬럼  
- 읽지 못한 것: 값 목록(예: Merchant.category에 어떤 값이 있는지, Member.segment_id의 숫자가 무슨 뜻인지).  
  명세에는 컬럼 이름과 자료형만 있음  

## 6. 값 목록 파일과 키 값 목록

### 개념 설명
값 목록 파일은 「분류에 쓸 수 있는 값은 이것뿐」이라고 적은 파일임. 5단계의 분류 규칙과 허용 값 검사가 이 파일만 읽음.  
키 값 목록은 다른 원천에 실제로 있는 키 값을 적은 파일임. 8단계에서 문서가 가리키는 대상이 정말 있는지 대조할 때 씀.  
둘 다 따로 정리된 파일이 없어, 아래 원본에서 옮겨 적은 파일을 만들지 사용자가 정해야 함. AI가 기억으로 적지 않음.  

| 만들 파일(추천) | 담을 값 | 옮겨 적을 원본 | AI가 확인한 것 |
|---|---|---|---|
| `{base_dir}/inputs/value_lists.json` | 업종 8개(식비, 쇼핑, 교통, 주유, 여행, 해외, 생활, 교육) | `backing-services/rdb/init/02_seed.sql`의 가맹점(merchant) 초기 데이터 | 가맹점 80행의 category 값이 이 8개뿐이고 값마다 10행임 |
| | 고객군 6개(1 신규 가입, 2 장기 보유, 3 VIP, 4 휴면 직전, 5 다중 카드, 6 연회비 부담) | `backing-services/rdb/init/01_schema.sql` 24행의 컬럼 설명 | member.segment_id는 1 ~ 6만 넣을 수 있게 막혀 있음(CHECK 조건) |
| `{base_dir}/inputs/key_values.json` | 상품 ID 64개(D2-C001 ~ D2-C064) | `backing-services/rdb/init/02_seed.sql`의 상품(product) 초기 데이터 | 상품 64행. 카드 혜택 청크의 card_id 64종과 범위가 같음 |

열 뜻  
- 만들 파일: 원본에서 값을 옮겨 적어 새로 만들 파일. 승인받은 뒤에만 만듦  
- 옮겨 적을 원본: 값이 실제로 적혀 있는 파일. DB에 접속하지 않고 저장소 안의 초기화 파일만 읽음  
- 업종: 가맹점을 나눈 분류. 고객군: 회원을 나눈 무리(상담 이력 파일도 고객군마다 하나씩 있음)  

- 어느 값을 분류 Class로 쓸지는 5단계에서 정함. 여기서는 파일을 만들지만 정함  
- 다른 값 목록 파일이 이미 있으면 그 경로를 알려 주시면 그것을 씀
