## 2단계: 역량 질문 정하기 `[단계 ①]`

한 일

- 여러 원천을 거치는 질문마다 건너가는 지점을 적음  

숫자(근거: `competency_questions.json`, `crossing_points.json`)  

| 항목 | 값 |
|---|---|
| 질문 유형 | 9가지 |
| 역량 질문 | 23개(사용자 질문에서 나온 것 20개, AI 제안 3개) |
| 범위별 | 문서 하나 15개(약관 4, 카드 혜택 안내 5, 상담 기록 6), 전체 모음 2개, 여러 문서 종류 3개, 문서와 다른 원천 3개 |
| 범위 밖으로 둔 질문 | 3개(카드별 연회비 금액, 이전 판 약관, 회원의 월별 사용액) |
| 건너가는 지점 | 6곳 |

온톨로지가 적용된 자리(요소: 답할 범위)  
- 기존 방식의 ①은 문서 종류마다 그 문서 안에서 답하는 질문만 정함. 이번에는 아래 두 가지가 더해짐  
- 더해진 것 1: 여러 원천을 거치는 질문 6개(M1 ~ M3, X1 ~ X3)를 문서 하나 범위 질문과 함께 정함  
- 더해진 것 2: 그 질문마다 원천이 바뀌는 자리와 「무엇으로 이어지는가」를 적은 건너가는 지점 표  

| 번호 | 거치는 원천 | 이어지는 것 | 다른 원천의 키 후보 |
|---|---|---|---|
| P1 | 상담 기록 → 약관 | 같은 주제 | 없음 |
| P2 | 상담 기록 → 카드 혜택 안내 | 같은 주제 | 없음 |
| P3 | 상담 기록 → 카드 혜택 안내 | 같은 대상(카드 상품) | Product.product_id |
| P4 | 정형 DB → 카드 혜택 안내 | 같은 분류 값(업종) | Merchant.category, 값 목록 8개 |
| P5 | 정형 DB → 상담 기록 | 같은 대상(회원) | Member.member_id, 값의 꼴이 달라 바꾸는 규칙 필요 |
| P6 | 정형 DB → 카드 혜택 안내 | 같은 대상(카드 상품) | Product.product_id, 키 값 목록 64개 |

- 이 표가 5단계의 출발점임: 「같은 대상」은 동일 규칙, 「같은 분류 값」은 분류 규칙과 허용 값, 「같은 주제」는 공통 개념 노드로 이어짐  
- 범위 밖으로 둔 「카드별 연회비 금액」은 「다른 원천이 가진 데이터는 그래프에 다시 싣지 않음」 원칙을 ① 단계에서 적용한 예임  

사용자 결정  
- 초안 그대로 승인함(검토 파일 `review/step2.md`). AI 제안 3개(R4, M3, X3)도 넣음

## 4단계: 스키마 후보 넓게 뽑기 `[단계 ②]`(온톨로지 적용 없음)

한 일  
- 발견용 표본을 1건씩 `SchemaFromTextExtractor.run(text=머리줄+단위, examples=그 문서 종류의 역량 질문)`에 넣음(`tools/extract_candidates.py`)  
- 앞서 나온 이름도, 공통 개념의 이름도 넘기지 않음. LLM은 Groq `openai/gpt-oss-120b`  

숫자(근거: `{문서 종류}/output/candidates_summary.md`, `candidates_calls.jsonl`)  

| 문서 종류 | 호출 | 실패 | 노드 이름 | 관계 이름 | 토큰 | 멈춤 |
|---|---|---|---|---|---|---|
| 약관 | 25 | 0 | 43 | 79 | 82,906 | 상한 25건을 모두 봄 |
| 카드 혜택 안내 | 67 | 0 | 29 | 59 | 245,269 | 묶음 5개 모두 새 타입이 3건 연속 없어 멈춤(10 ~ 16건) |
| 상담 기록 | 22 | 1 | 23 | 50 | 93,619 | 묶음마다 3 ~ 4건을 모두 봄 |

- 실패 1건: LLM이 같은 속성에 EXISTENCE와 KEY 제약을 겹쳐 넣어 스키마 검증에 실패함. 사유를 적고 넘어감  

교재에 쓸 만한 관찰(온톨로지를 적용하지 않은 ②의 한계)  
- 세 문서 종류 어디에서도 **문서끼리 이어 줄 공통 개념(주제)이 후보에 나오지 않음**. LLM은 단위 하나만 보므로 다른 문서와 이어질 자리를 모름  
- 카드(혜택 안내 67번, 상담 18번), 회원(상담 21번), 거래 집계(상담 8번)처럼 **정형 DB가 이미 가진 대상**이 노드 후보로 많이 나옴  
- 혜택 안내의 시행일(effective_date)은 42번 나왔지만 어느 역량 질문에도 쓰이지 않음(빈도와 필요는 다름)  
- 불만(Complaint)과 제안(Proposal)은 1번씩만 나왔지만 역량 질문 C1, C3, M1, M2, A2에 꼭 필요함  
- 상담 기록 후보에 전화번호, 생년월일, 이메일 같은 개인정보 속성이 나옴  

## 5 ~ 6단계: 스키마 초안과 공통 개념 층 초안 `[단계 ③]`

- 문서 종류별 스키마 초안을 스크립트로 만듦. Class에 대응하는 노드 타입의 description 첫머리는 공통 개념 층의 뜻을 스크립트가 넣음(`tools/build_schema.py`)  
- 6단계 기계 검증(`common/tools/check_concepts.py`)과 그림 미리보기 확인  

온톨로지가 적용된 자리(요소별)  

| 요소 | 이번 설계에서 정한 것 |
|---|---|
| Class 정의 | 9개: 카드상품, 회원, 고객군, 업종, 주제(공통 노드), 조항, 혜택, 상담, 불만. 뜻 한 줄은 공통 개념 층에만 둠 |
| 동일 | 카드상품: 혜택 안내와 정형 DB는 값 같음, 상담 기록은 바꾸는 규칙(카드 이름 → 상품 ID 표 64쌍). 회원: 바꾸는 규칙(SHA-256 앞 16자리 + m_). 업종: 맞추기 표. 주제: 이름 맞추기 |
| 분류 | 고객군 6개, 업종 8개(값 목록 파일에서만 읽음). 두 목록 모두 상하위 없음 |
| 개념 | 관계 6개마다 출발과 도착 Class(예: ABOUT은 불만, 조항, 혜택 → 주제) |
| 역관 | TOPIC_OF, SEGMENT_OF, FOLLOWED_BY, CATEGORY_OF(반대 방향으로 묻는 질문이 있는 관계에만) |
| 검사 규칙 | 허용 값 2개, 허용 수 4개, 참조 무결성 3개는 검사 규칙으로, 값 겹침 금지 1개는 스키마 제약(UNIQUENESS)으로 |

숫자  

| 항목 | 값 |
|---|---|
| 스키마 초안 | 약관 노드 2, 관계 2 / 카드 혜택 안내 노드 3, 관계 1 / 상담 기록 노드 6, 관계 6 |
| 공통 노드 | Topic 1개(세 문서에 같은 라벨, description, 속성, 키) |
| 인덱싱이 더하는 것 | 라벨 Category, 관계 IN_CATEGORY(맞추기 표) |
| 상담 기록의 카드상품 키 규칙 | 48건 중 48건에서 상품 ID를 찾음(카드를 둘 말한 4건은 기록 문장의 카드) |

| 되돌아감 | 0회(상한 5회) |

후보에서 바뀐 것(추천표의 요지)  
- 참조: 카드, 회원은 노드를 만들지 않고 키 속성(product_id, member_pseudo_id)만 둠  
- 분류: 업종 비슷한 이름 5개(MerchantCategory 등)는 업종 Class로. LLM이 뽑지 않고 인덱싱이 맞추기 표로 더함  
- 추가: 주제(공통 노드), 이용 기준(UsageRule), 상담의 진행 상태(progress), 제안의 수락 여부(accepted)  
- 제거: 시행일, 상담사, 거래 집계, 개인정보 속성, 조항 안의 일반 낱말 38개  

사용자 결정  
- 초안 그대로 승인함(검토 파일 `review/step5.md`)

## 교재용 요약: 설계 단계마다 온톨로지가 바꾼 것과 근거 숫자

| 설계 단계 | 기존 방식 | 온톨로지 적용 | 이번 실행의 근거 |
|---|---|---|---|
| ① 역량 질문 | 문서 종류마다 그 문서 안의 질문만 | 여러 원천을 거치는 질문과 건너가는 지점(답할 범위) | 역량 질문 23개 중 6개가 여러 원천 범위. 건너가는 지점 6곳(같은 대상 3, 같은 분류 값 1, 같은 주제 2) |
| ② 후보 추출 | LLM이 문서만 보고 후보 | 적용하지 않음(새 개념이 들어설 자리를 남김) | 노드 이름 95개 뽑힘. 공통 개념(주제)은 0번, 정형 DB가 가진 카드와 회원은 100번 넘게 나옴 |
| ③ 후보 확정 | 병합, 제거, 추가로 스키마만 | Class 정의, 동일, 분류, 개념, 역관, 검사 규칙을 스키마와 함께 | Class 9, 카드와 회원은 노드 없이 키만, 업종과 고객군은 값 목록에서만, 주제는 공통 노드 |
| ④ 채우기 시험 | 질문별 지표만 | 검사 규칙 위반 수와 경로 이어짐도 셈 | 질문 지표가 좋아도 키가 빠진 혜택 10개를 경로 검사가 잡음. 주제 이어짐 2/11 → 7/10, 규칙 위반 20 → 1 |
| ⑤ 스키마 확정 | 스키마만 저장 | 공통 개념 층을 함께 저장 | `common/concepts.json` 판 1. 다음 설계의 ③이 이 층을 읽음 |

교재에 쓸 만한 장면 다섯 가지  
1. ② 결과에 공통 개념이 없음: LLM은 단위 하나만 보므로 다른 문서와 이어질 자리를 모름(4단계)  
2. 사람도 LLM도 주제 이름을 따로 지으면 이어지지 않음: 기대 답 주제 이름 겹침 0(7단계), 라운드 1 이어짐 2/11(8단계)  
3. LLM의 대표 주제 초안은 허브를 만듦: 「혜택」 하나에 22개 이름, 가짜 연결 3건 → 사람이 보류하고 옮겨 7/10(8단계 라운드 2 ~ 4)  
4. 머리줄 값은 LLM에 맡기지 않음: LLM이 상품 키를 빠뜨려(22/32) 스크립트가 넣도록 바꾸자 100%, 위반 0(F1)  
5. 고치면 다른 것이 깨짐: JSON 모드를 끄자 응답이 잘려 관계가 사라짐 → 시험(④)을 다시 돌려 잡음(시행착오 3)
