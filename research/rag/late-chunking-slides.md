## 슬라이드 1. Late Chunking

- 제목: Late Chunking: 문서 전체를 먼저 임베딩하고 나중에 자르기
- 리드문: 긴 문맥 임베딩 모델에 문서 전체를 한 번 통과시킨 뒤, 토큰 벡터를 청크 구간별로 평균 내어 문맥을 보존합니다.
- 좌상 배지: 왜 필요한가
- 좌상 카드:
  - 질문: 베를린의 인구는?
  - 청크: "Its more than 3.85 million inhabitants..."
  - "Its"가 무엇인지 몰라 Berlin 질문에 안 걸림
  - Late 적용 뒤 Berlin과 유사도 0.71 → 0.82
- 좌하 배지: 실습 적용(Chroma + Cohere)
- 좌하 카드:
  - Cohere API는 토큰 벡터를 안 줘 적용 불가
  - 대안: Jina API late_chunking 또는 jina-v3 로컬
  - 질문도 같은 모델로 임베딩, Chroma에는 벡터만
- 중앙 배지: 처리 절차
- 처리 절차:
  1. 기존 splitter로 청크 경계를 정함(경계는 여전히 필요)
  2. 문서 전체를 토큰화하고 글자 경계를 토큰 구간으로 바꿈
  3. 모델을 한 번 통과시켜 토큰 벡터를 얻음(모든 토큰이 문서 전체를 봄)
  4. 청크 구간별로 토큰 벡터를 평균 내어 청크 벡터를 만듦
- 우상 배지: 효과(nDCG@10, jina-embeddings-v3)
- 표 열 너비: [2.0, 1.6, 1.6]

| 데이터셋 | 기존 청킹 | Late |
|---|---|---|
| SciFact | 71.8 | 73.2 |
| NFCorpus | 35.6 | 36.7 |
| FiQA | 46.3 | 47.6 |
| TRECCOVID | 73.0 | 77.2 |

- 우하 배지: 한계
- 우하 카드:
  - 토큰 벡터를 주고 문서를 통째로 담는 긴 문맥 평균 풀링 모델 필요
  - 글은 그대로라 BM25 효과 없음. 짧은 문서는 이득 작음
- 콜아웃: LLM 호출 없이 문맥을 얻지만, 독립 비교(NFCorpus nDCG@10)에서는 Contextual 0.308 대 Late 0.294로 뒤졌습니다.
- 상세 보기 링크: https://github.com/unicorn-campus/hybrid-ai/blob/main/research/rag/late-chunking.md
- 화면 출처: Günther 외, Late Chunking (arXiv 2409.04701 v3). Jina AI 블로그 1편(2024-08-22)과 2편(2024-10-03). voyage-context-3, context-4 (Voyage AI, MongoDB)
- 발표자 노트:
  - 핵심 한 줄: 기존 방식은 "자르고 나서 임베딩"이라 청크끼리 서로 못 봅니다. Late Chunking은 "임베딩하고 나서 자르기"라서 토큰 벡터 하나하나에 문서 전체 정보가 섞인 뒤에 청크 구간별로 평균을 냅니다. 추가 학습도 LLM 호출도 없습니다.
  - 블로그 예시: 베를린 위키 문서를 문장 단위로 자르면 "Its more than 3.85 million inhabitants make it the European Union's most populous city..." 문장에 Berlin이라는 단어가 없습니다. 논문 표 1(jina-embeddings-v2-small)에서 이 문장과 "Berlin"의 코사인 유사도는 기존 0.7084, Late 0.8249입니다. 다른 두 문장도 0.75에서 0.85, 0.85에서 0.85로 같거나 올랐습니다.
  - 처리 절차 보충: 경계 단서는 여전히 필요하고, 쓰는 시점만 모델 통과 뒤로 밀립니다. 코드는 tokenizer의 offset mapping으로 글자 위치를 토큰 번호 구간으로 바꾸고, 구간의 토큰 벡터를 더해 개수로 나눕니다(공식 저장소 chunked_pooling). 블로그 1편은 "앞 청크에 조건화"라고 썼지만 2편이 "양방향"으로 바로잡았습니다.
  - 긴 문서: 모델 한도 8192토큰을 넘으면 long late chunking(논문 v3 3.1절)을 씁니다. 큰 창으로 나눠 각각 통과시키되 창끼리 512토큰을 겹쳐 문맥을 보충하고, 겹친 앞부분 출력은 버리고 이어 붙입니다.
  - 효과 표 조건: 고정 256토큰 청크, 겹침 없음, BEIR 4개 데이터셋, nDCG@10(상위 10개 순서 점수, 높을수록 좋음). 3개 모델 평균 상대 향상은 고정 크기 +3.46%, 문장 경계 +3.63%, 의미 경계 +2.70%입니다. 문서가 길수록 이득이 크고(NFCorpus 평균 1,589자 +6.5점, Quora 62자 변화 없음), 청크가 작을수록 이득이 큽니다.
  - 지원 모델: Jina API는 요청에 late_chunking: true를 주면 되고, 2026년 10월 OpenAPI 명세 기준 jina-embeddings-v3와 v4에만 있습니다(v2, v5 없음). 로컬 실행은 jina-embeddings-v3(572M, 약 2.1GB, trust_remote_code 필요)이며 라이선스가 CC BY-NC 4.0이라 상업 이용은 문의가 필요합니다. 일반 조건은 토큰 벡터 접근 가능, 8192 이상 긴 문맥, 평균 풀링 모델입니다. CLS나 max 풀링 모델은 부적합합니다.
  - 한계와 독립 비교: 1차 출처가 모두 Jina 측 자료입니다. 독립 비교(arXiv 2504.19754, NFCorpus 20% 부분집합, jina-v3, 512토큰 청크)에서 nDCG@10은 Late 0.294, Contextual Retrieval 0.308이었습니다. 다만 Contextual 쪽에 BM25 결합과 리랭커가 포함되어 순수 비교는 아닙니다. 같은 연구에서 BGE-M3는 NFCorpus 0.225에서 0.067로 크게 떨어져, 모델을 가려 써야 합니다.
  - 실습 적용 포인트: Cohere embed API는 텍스트마다 최종 벡터 하나만 주므로 구간 평균을 낼 토큰 벡터가 없습니다. 적용하려면 임베딩 모델을 Jina로 바꿔야 하고, 질문 벡터도 같은 모델로 만들어야 하며 기존 Cohere 인덱스와 섞을 수 없습니다. BM25 색인과 청크 문장은 그대로 씁니다. Chroma에는 미리 계산한 벡터를 upsert의 embeddings 인자로 넣습니다. 상세 문서 9절에 Jina API 방식과 로컬 방식 Python 예시가 있습니다.
  - Contextual Retrieval과의 차이: Contextual은 글 자체에 문맥을 써 넣어 임베딩과 BM25가 함께 좋아지지만 청크마다 LLM 비용이 듭니다. Late Chunking은 비용이 거의 없지만 글이 바뀌지 않아 BM25에는 영향이 없고 모델 제약이 큽니다.

## 슬라이드 2. Late Chunking 원리 도식

- 제목: Late Chunking 원리: 자르는 시점만 모델 통과 뒤로 옮깁니다
- 리드문: 청크 경계는 똑같이 미리 정합니다. 다른 점은 모델에 청크를 따로 넣느냐, 문서 전체를 한 번에 넣고 나서 나누느냐입니다.
- 시각 배치: 왼쪽 10.45″에 위아래 두 줄 흐름도(위: 기존 방식, 아래: Late Chunking). 토큰 9개를 3색(청크 1 파랑, 청크 2 네이비, 청크 3 다크)으로 단순화해 그림.  
  오른쪽 4.16″에 베를린 예시 카드와 유사도 표. 아래 콜아웃 한 줄, 「상세 보기」 필 라벨, 출처 한 줄
- 상단 배지: 기존 방식: 자르고 나서 임베딩 (chunk → embed)
- 상단 라벨: 같은 모델을 3회 호출. 청크끼리 서로 못 봄
- 상단 캡션: "Its more than 3.85 million..." 청크만 보면 모델은 "Its"가 무엇인지 알 수 없음
- 하단 배지: Late Chunking: 임베딩하고 나서 자르기 (embed → chunk)
- 하단 캡션: 저장하는 벡터 수와 검색 방식은 그대로. 바뀌는 것은 벡터에 담긴 문맥뿐
- 도식 문서 제목: 문서 (토큰 9개로 단순화)
- 도식 문서 캡션 상단: 청크 경계는 미리 정함
- 도식 문서 캡션 하단: 같은 경계, 적용만 나중에
- 도식 청크 라벨: 청크
- 도식 모델 상단: 임베딩 모델
- 도식 평균 상단: 토큰 평균
- 도식 벡터 라벨: 벡터
- 도식 모델 하단: 임베딩 모델 1회 통과 (긴 문맥 모델 필요)
- 도식 토큰 제목: 토큰 벡터 9개
- 도식 토큰 캡션: 각 토큰이 문서 전체를 봄 (양방향)
- 도식 평균 하단: 구간별 토큰 평균
- 우측 배지: 예시: 베를린 문서를 문장 3개로 자름
- 우측 카드:
  - 문장 1: "Berlin is the capital and largest city..."
  - 문장 2: "Its more than 3.85 million inhabitants..."
  - 문장 3: "The city is also one of the states..."
- 표 열 너비: [1.757, 1.2, 1.2]

| 문장 | 기존 | Late |
|---|---|---|
| 문장 1 | 0.8486 | 0.8495 |
| 문장 2 | 0.7084 | 0.8249 |
| 문장 3 | 0.7535 | 0.8498 |

- 표 캡션: "Berlin"과의 코사인 유사도 (Jina 논문 표 1)
- 풀링 라벨: 평균 풀링(토큰 평균)이란?
- 풀링 토큰 라벨: 토큰 벡터
- 풀링 토큰: [0.2, 0.9] / [0.4, 0.5] / [0.6, 0.1]
- 풀링 계산: 자리별로 더해 ÷ 3
- 풀링 결과: [0.4, 0.5]
- 풀링 설명: 청크 벡터 1개 (임베딩 API 안에서 늘 하는 일)
- 콜아웃: 경계는 같고, 모델을 자르기 전에 통과시키느냐 뒤에 통과시키느냐가 다릅니다. 모델 한도(예: 8192토큰)를 넘는 문서는 나눠 처리합니다.
- 상세 보기 링크: https://github.com/unicorn-campus/hybrid-ai/blob/main/research/rag/late-chunking.md#3-원리와-처리-절차
- 화면 출처: Günther 외, Late Chunking (arXiv 2409.04701 v3) 표 1과 알고리즘 1. Jina AI 블로그 2편(2024-10-03)
- 발표자 노트:
  - 위 줄(기존 방식): 문서를 청크 3개로 자른 뒤 청크마다 임베딩 모델을 따로 통과시킵니다. 모델은 같은 모델 하나이고 3회 호출하는 것입니다. 모델이 한 번에 보는 글이 청크 하나뿐이라, "Its"가 베를린을 가리킨다는 정보가 벡터에 들어가지 못합니다.
  - 아래 줄(Late Chunking): 같은 청크 경계를 쓰되, 문서 전체를 긴 문맥 임베딩 모델에 한 번 통과시켜 토큰 9개 각각의 벡터를 먼저 얻습니다. 임베딩 모델은 모든 토큰이 서로를 보는 양방향 구조라 토큰 벡터마다 문서 전체 정보가 섞입니다. 그 뒤 청크 경계대로 토큰 벡터를 구간별로 평균 내면 청크 벡터 3개가 나옵니다.
  - 바뀌지 않는 것: 청크 수, 저장하는 벡터 수, 벡터DB 검색 방식은 기존과 같습니다. 바뀌는 것은 벡터에 담긴 문맥뿐이라 검색기 코드는 손대지 않아도 됩니다.
  - 전제: 토큰별 벡터를 내주는 모델이어야 하고(Cohere embed API처럼 최종 벡터 하나만 주는 API는 불가), 문서 전체를 담을 긴 문맥 모델이어야 합니다. 모델 한도(jina-embeddings-v3는 8192토큰)를 넘는 문서는 큰 창으로 나눠 통과시키고 창끼리 512토큰을 겹쳐 문맥을 보충합니다(논문 v3의 long late chunking).
  - 토큰 9개는 설명을 위한 단순화입니다. 실제로는 청크 하나가 수십에서 수백 토큰입니다. 글자 경계를 토큰 구간으로 바꿀 때는 tokenizer의 offset mapping을 씁니다.
  - 오른쪽 표: 논문 표 1의 값으로, jina-embeddings-v2-small에서 각 문장 임베딩과 "Berlin" 임베딩의 코사인 유사도입니다. 베를린이라는 단어가 없는 문장 2가 0.7084에서 0.8249로 가장 크게 올랐습니다.
  - 아래 띠(평균 풀링): 임베딩 모델은 토큰마다 벡터를 하나씩 만들고, 벡터DB에는 청크당 벡터 1개를 저장하므로 이를 하나로 합쳐야 합니다. 가장 흔한 방법이 평균 풀링으로, 같은 자리끼리 더해 개수로 나눕니다. 예시에서 첫째 자리는 (0.2 + 0.4 + 0.6) ÷ 3 = 0.4, 둘째 자리는 (0.9 + 0.5 + 0.1) ÷ 3 = 0.5입니다. 실제 벡터는 2칸이 아니라 수백에서 수천 칸입니다. 실습의 Cohere API는 이 단계를 서버 안에서 끝내고 결과 벡터만 돌려주기 때문에 실습 코드에는 드러나지 않습니다. Late Chunking은 이 단계를 사용자가 직접 하되, 문서 전체를 본 토큰 벡터를 청크 구간별로 평균한다는 점만 다릅니다.
