## 슬라이드 2. 큰 흐름 7가지 (패턴 A 변형: 넘버 배지 리스트 2열)

- 제목: 2026년 RAG의 큰 흐름 7가지
- 리드문: 검색은 "파이프라인 단계"에서 "에이전트가 반복 호출하는 도구"로 바뀌고, 하이브리드와 평가가 기본이 됨
- 본문: 넘버 배지(1 ~ 7) + 제목(Bold) + 한 줄 설명. 좌열 4개, 우열 3개
  1. 하이브리드 + 리랭킹이 기본 구성 — Anthropic 실험과 주요 벡터DB의 네이티브 지원이 같은 방향
  2. 검색이 "단계"에서 "도구"로 — NL2SQL 탐색 루프, 에이전틱 RAG, 딥 리서치, 적시 검색
  3. 모델보다 "정의된 지식"이 정확도를 올림 — 시맨틱 레이어, 메트릭 정의, 메타데이터
  4. 그래프와 긴 문맥은 대체가 아니라 보완 — 질문 유형별 라우팅이 권고됨
  5. 비용이 설계 기준 — 지연 구축, 소형 리랭커 미세조정, 멀티벡터 압축, MCP 점진 공개
  6. "자르고 나서 문맥을 되살리는" 색인이 표준 옵션 — Contextual Retrieval, late chunking, Docling
  7. 벤더 수치는 독립 재현 필요 — 그래프 메모리 독립 평가에서 RAG보다 20%p 이상 낮은 사례

## 슬라이드 4. BM25와 희소 검색 (패턴 A: 2단 헤더 바)

- 제목: BM25와 희소 검색: 2026년에도 BM25가 중요한 이유
- 리드문: 정확 일치가 중요한 문서에서 BM25가 임베딩을 앞서고, 한국어는 형태소 분석기가 곧 검색 품질임
- 본문 좌측(w 7.2): 네이비 헤더 바 「왜 여전히 강한가」 + 틴트 박스
  - 금융 문서 벤치마크(2026)에서 BM25가 text-embedding-3-large를 대부분 지표에서 앞섬
  - 고유명사, 제품번호, 오류 코드 같은 정확 일치 질의에 임베딩이 약함
  - Anthropic 실험: "임베딩 + BM25"가 임베딩 단독보다 나음
  - BM25S(2024): 색인 시점 점수 계산으로 파이썬 BM25 대비 최대 500배 빠름
- 본문 우측(w 7.2): 블루 헤더 바 「한국어와 학습형 희소 검색」 + 넘버 배지 리스트
  1. 한국어는 조사와 어미 때문에 공백 분리가 실패. Kiwi 형태소 분석기로 어간 추출
  2. 소규모 실측: 공백 BM25 Top3 정답 11/15, Kiwi BM25 15/15
  3. 형태소 분석기 버전 고정, 교체 시 재색인
  4. SPLADE 계열은 BEIR에서 BM25를 앞서지만 GPU 추론 필요, 사전 밖 토큰에 약함
  5. OpenSearch는 BM25, Nori, kNN, RRF를 엔진 기능으로 제공

## 슬라이드 5. 하이브리드 검색과 리랭킹 (흐름 도식 + 표)

- 제목: 하이브리드 검색과 리랭킹: 사실상의 기본 구성
- 리드문: "BM25 + 벡터 → RRF 융합 → 리랭커"가 기본값이 되었고, 융합 방식보다 리랭커 유무가 결과를 더 좌우함
- 본문 상단(y 1.90 ~ 3.1): 흐름 도식. 라운드 박스 5개를 화살표(→)로 연결
  - [질문] → [BM25 검색] + [벡터 검색] → [RRF 융합 (k=60)] → [리랭커 (크로스 인코더 또는 LLM)] → [상위 N 전달]
  - 도식 아래 한 줄: Anthropic 실험에서 리랭킹까지 더하면 상위 20개 검색 실패율 5.7% → 1.9% (67% 감소)
- 본문 하단 좌측(w 7.2): 다크 배지 「융합 전략 비교」 + 표
  | 전략 | 장점 | 단점 |
  | RRF (k=60) | 설정 없이 동작, 정규화 불필요 | 점수 크기 차이를 구분 못 함 |
  | 가중 합성 | 레이블 질의가 있으면 더 나을 수 있음 | min-max 정규화가 짧은 목록에 불안정 |
  | 학습형 융합 | 대규모에서 개선 주장 | 학습 데이터 필요 |
- 본문 하단 우측(w 7.2): 다크 배지 「리랭커 선택 기준」 + 틴트 박스
  - 자체 호스팅 기본: bge-reranker-v2-m3. 오픈 최고 성능 후보: Qwen3-Reranker. 관리형: Cohere, Voyage
  - 크로스 인코더 상위 100개 p50 약 140ms, LLM 리랭커 상위 50개 약 700ms, 품질 차이는 작음(2차 자료)
  - 도메인 데이터가 있으면 109M 크로스 인코더 미세조정이 4B LLM 리랭커를 이김(2026 연구)
  - listwise LLM 리랭커는 어려운 질의에만 3단계로
- 상세 보기 링크: `#5-하이브리드-검색과-리랭킹`
- 출처: Anthropic Contextual Retrieval, redis.io(RRF), bigdataboutique.com(융합 비교), arXiv 2608.09650

## 슬라이드 7. 그래프 검색 GraphRAG (패턴 A: 언제 쓰고 언제 안 쓰나)

- 제목: 그래프 검색 GraphRAG: 전부 대신 보완, 비용이 설계 기준
- 리드문: 전체 조망과 다중 홉에는 유리하지만 단순 사실형에는 불리하며, 저비용 변형(LazyGraphRAG, HippoRAG 2, EffiRAG)으로 이동함
- 본문 좌측(w 7.2): 네이비 헤더 바 「유리한 경우와 대표 기법」 + 넘버 배지 리스트
  1. 여러 문서를 엮는 복합 추론, 전체 조망 요약, 관계 탐색
  2. LazyGraphRAG(MS, 2024-11): 질의 때 요약. 인덱싱 비용 전체 GraphRAG의 0.1%(벤더 발표)
  3. HippoRAG 2(ICML 2025): PageRank로 그래프를 타되 원문 구절 결합
  4. EffiRAG(2026-09): 그래프로 위치만 찾고 답은 원문에서. LightRAG 대비 비용 57% 절감
  5. Text-to-Cypher는 Text-to-SQL보다 어림. CypherBench GPT-4o 60.18%
- 본문 우측(w 7.2): 블루 헤더 바 「쓰지 말아야 할 경우」 + 틴트 박스
  - 질문 대부분이 한 문단 안에 답이 있는 단일 홉 사실형일 때 (NQ에서 GraphRAG가 바닐라 RAG보다 13.4% 낮음)
  - 시간 민감 질문이 많을 때 (그래프가 "언제"를 잘 담지 못함)
  - 추출 품질을 검증할 평가셋이 없을 때 (추출 오류가 답에 전파)
  - 인덱싱 예산이 벡터 RAG의 수십 배를 감당하지 못할 때 (LightRAG 8,680만 토큰 사례)
  - 벡터 RAG에 리랭킹만 붙여도 목표 품질에 닿을 때
  - 그래프 메모리(Graphiti, cognee) 독립 평가: RAG보다 20%p 이상 낮음
- 상세 보기 링크: `#7-그래프-검색-graphrag`
- 출처: Microsoft Research(LazyGraphRAG), arXiv 2506.05690(GraphRAG-Bench), arXiv 2609.18099(EffiRAG), arXiv 2601.07978

## 슬라이드 8. 온톨로지와 지식그래프 (패턴 B 변형: WHY, HOW, WHAT 3행 + 우측 카드)

## 슬라이드 10. 에이전틱 RAG와 딥 리서치 (루프 도식 + 표)

- 제목: 에이전틱 RAG와 딥 리서치: 검색이 루프 안의 도구가 됨
- 리드문: LLM이 "검색할지, 무엇을, 다시 할지"를 판단하고, 딥 리서치는 계획, 병렬 검색, 종합, 인용의 다단계로 보고서를 만듦
- 본문 상단(y 1.90 ~ 3.1): 루프 도식. 라운드 박스 5개 + 되돌아가는 화살표
  - [질문 분석] → [검색 도구 호출 (벡터, 키워드, SQL, 웹)] → [문서 등급 판정] → [부족하면 질의 재작성 후 재검색] → [근거 기반 생성 + 환각 검사]
- 본문 하단 좌측(w 7.2): 다크 배지 「대표 기법」 + 표
  | 기법 | 요점 |
  | Self-RAG, CRAG | 반성 토큰, 문서 등급으로 재검색 판단 |
  | LangGraph Adaptive RAG | 라우터 + 등급 + 재작성 + 환각 검사 루프 |
  | Azure agentic retrieval | 하위 질의 분해 후 병렬 검색, 시맨틱 리랭킹 |
  | Search-R1 (COLM 2025) | 강화학습으로 검색 시점과 질의를 학습. RAG 대비 +24% |
- 본문 하단 우측(w 7.2): 다크 배지 「딥 리서치 구조와 비용」 + 틴트 박스
  - Anthropic Research: 오케스트레이터-워커 구조, 단일 모델 대비 90.2% 향상
  - 토큰 사용량이 성능 분산의 80%를 설명, 일반 채팅 대비 약 15배 토큰
  - 서브에이전트에 목표, 출력 형식, 도구, 범위를 명확히 주지 않으면 중복 작업
  - 오픈소스: LangChain Open Deep Research(범위 → 조사 → 쓰기), GPT Researcher
  - 질문당 예산 상한과 검색 횟수 상한을 둠

## 슬라이드 11. 컨텍스트 엔지니어링과 긴 문맥 논쟁 (패턴 D: 비교표 + 카드)

- 제목: 컨텍스트 엔지니어링: 긴 문맥은 RAG의 대체가 아니라 라우팅 대상
- 리드문: 문맥은 유한 자원(주의 예산)이며, 단순 조회는 RAG로, 문서 간 종합은 긴 문맥으로 보내는 설계가 권고됨
- 본문 좌측(w 7.6): 다크 배지 「긴 문맥 vs RAG (LaRA, ICML 2025)」 + 표
  | 과제 유형 | 유리한 쪽 | 비고 |
  | 단일 위치 사실 조회 | RAG | 약한 모델일수록 RAG 이득이 큼 |
  | 환각 탐지 | RAG | 근거가 좁을수록 검증이 쉬움 |
  | 추론과 비교 과제 | 긴 문맥 | 문서 간 관계를 한 번에 봄 |
  | 반복 사용 문서 묶음 | 긴 문맥 + 캐싱 | 캐시 적중 $0.10/MTok (Sonnet 5.5, 2026-10 열람) |
  | 자주 바뀌는 문서, 사용자별 문서 | RAG | 캐시 적중률이 떨어짐 |
- 본문 우측(w 6.8): 블루 헤더 바 「Anthropic 가이드 (2025-09)」 + 틴트 박스
  - 주의 예산: 토큰이 늘수록 집중력이 분산됨(context rot)
  - 적시 검색: 파일 경로, 저장된 질의, 링크만 두고 필요할 때 도구로 불러옴
  - 긴 작업: 압축, 구조화된 메모, 서브에이전트 분리
  - MCP 도구 정의는 점진 공개. 코드 실행 방식으로 150,000 → 2,000 토큰(98.7% 절감)

- 출처: Anthropic 컨텍스트 엔지니어링 가이드, ICML 2025(LaRA), Anthropic Code execution with MCP, docs.claude.com(프롬프트 캐싱)

## 슬라이드 12. RAG 평가와 관측 (패턴 A: 2단)

- 제목: RAG 평가와 관측: 자사 평가셋과 실행 추적이 설계의 일부
- 리드문: 검색과 생성을 나눠 재고, LLM 심사자는 고정과 보정으로 쓰며, 에이전트형 검색은 추적 없이는 원인을 못 찾음
- 본문 좌측(w 7.2): 네이비 헤더 바 「지표와 평가셋」 + 넘버 배지 리스트
  1. faithfulness: 답이 검색 문맥에 근거하는가
  2. answer relevancy: 답이 질문에 맞는가 (정답 여부는 아님)
  3. context precision과 recall: 가져온 청크의 관련 비율과 누락 여부
  4. RAGAS 테스트셋 생성: 문서로 지식 그래프를 만들어 단일 홉과 다중 홉 질문 생성
  5. 실패 → 테스트 변환: 운영 로그의 실패 질문을 평가셋에 추가
  6. NL2SQL은 질문, 정답 SQL, 실행 결과 3종으로 채점
- 본문 우측(w 7.2): 블루 헤더 바 「LLM 심사자와 관측 도구」 + 틴트 박스
  - 심사 모델 고정, 사람 라벨 소규모 집합으로 보정, 절대값 대신 추세 추적
  - 집계 점수는 개별 실패를 가림. 실패 사례를 직접 열람
  - LangSmith(LangChain 스택), Langfuse(프레임워크 독립, MIT), Arize Phoenix(OpenTelemetry)
  - OpenTelemetry로 계측하면 백엔드를 나중에 바꿀 수 있음
  - RAGAS 0.4.x 기준. 옛 클래스명은 1.0에서 제거 예정
- 상세 보기 링크: `#12-rag-평가와-관측`
- 출처: docs.ragas.io, letsdatascience.com(LLM-as-judge), signoz.io(관측 도구 비교), Anthropic 멀티 에이전트 리서치 글
