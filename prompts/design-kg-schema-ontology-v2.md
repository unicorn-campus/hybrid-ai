[목표]

사람이 승인한 업무 온톨로지 원본과 RDB 조회 매핑 및 문서별 추출 스키마를 처음부터 함께 설계하고 검증함

모든 확정 판단을 원천 자료와 실행 결과로 뒷받침합니다.

## Phase 1 입력 자료와 원천 확인 `[승인]`

### Step 1.1 정형 데이터(RDB)

- RDB는 `SELECT 1`로 접속을 확인하고 세션을 읽기 전용으로 둠. 비밀번호와 키 값은 출력하지 않고  
  존재 여부만 확인함. 접속 실패는 세 번까지 입력을 고쳐 확인한 뒤 중단함.  

- 입력받은 범위에서 제외 스키마를 먼저 뺍니다. 구조 조사 계정으로 대상 스키마의 모든 일반 테이블, 열과 자료형,  
  PK, UNIQUE, FK 제약을 확인합니다. 복합 FK는 제약 하나로 세고 열 짝의 순서를 보존합니다.  

- 지정한 뷰 스키마의 모든 뷰에서 결과 열, 참조 대상, 조인, 필터와 집계 기준을 확인합니다. 뷰 정의로 간접 참조를,  
  앱 조회 SQL로 직접 호출을 확인해 `structure.json`에 함께 기록합니다. 직접 호출 근거가 없으면 ‘미확인’으로 둡니다.  

- 실제 조회는 입력받은 앱 계정과 세션 조건으로 검증합니다. 앱에 허용된 조회 경로에서 안정된 키 순서와  
  건수 상한을 정해 표본을 읽고, 코드값과 키 확인에 필요한 값만 가명 처리해 `rdb_samples.json`에 남깁니다.  

### Step 1.2 비정형 문서

- Chroma는 `list_collections()`와 `get_collection()`으로 기존 collection만 열고, 청크 ID, 본문, 메타데이터만 읽음.  
  collection 건수, ID 중복, 빈 본문과 빈 메타데이터를 확인하고 ID 순으로 `chunks_snapshot.json`에 고정함.  

- 문서에 개인정보 형태가 남아 있으면 값은 가리고 건수와 위치만 보고함. 외부 LLM 전송 여부를 승인받기 전에는  
  전송하지 않음.  

### Step 1.3 공통 확인과 기록

- `neo4j-graphrag`, `chromadb`, `rdflib`, `pyshacl`의 설치 여부와 버전을 확인함. Chroma 버전은 인덱서에서 사용한 Chroma 버전과 맞춤.  
- 입력 파일과 도구 버전, 내용 지문을 `sources.json`에 기록함.  
- 출력파일: `structure.json`, `rdb_samples.json`, `chunks_snapshot.json`, `sources.json`, `decisions.json`  

## Phase 2 역량 질문 작성과 범위 정하기 `[승인]`

### Step 2.1 용도 확인

[역량 질문 가이드](../references/how-to-competency-question.md) 2절에 따라 업무, 사용 목적,  
질문 유형 확인. 누구의 업무와 표현을 기준으로 질문을 쓸지 정하기 위해 실제 사용자 확인.  
용어나 업무 기준이 모호할 때 문의할 담당자 역할 확인. 담당자를 알 수 없으면 ‘미지정’으로 표시.  

### Step 2.2 원본 평가셋 전체 검토

모든 문항을 설계용 보완본에 포함하고 원본 문항 번호와 출처 보존.  

### Step 2.3 설계용 평가셋 보완

사용자가 업무에서 내려야 할 판단과 기존 문항의 질문, 정답, 근거 위치, 단서를 대조해 빠진 질문 확인.  
후보마다 Phase 1의 RDB 구조와 문서 청크를 검토하고, 답에 필요한 DB 값이나 문서 구절을 실제로 확인할 수 있는지 점검.  
정답과 근거를 확인한 문항은 번호를 부여해 보완본에 추가. 업무에 필요하지만 근거가 부족한 항목은 부족한 자료와 함께 보류.  
추가 문항과 보류 사유를 사용자에게 보여 주고 설계용 보완본 확정. 원래부터 ‘답 없음’을 시험하는 문항은 그 취지대로 유지.  

### Step 2.4 질문 유형 분류

확정된 설계용 보완본에서 사람 이름이나 상품명처럼 사례마다 달라지는 값을 일반화하고 같은 의도의 문항끼리 묶음.  
각 묶음에 ‘혜택 금액 확인’, ‘신청 기한 확인’처럼 질문 의도가 드러나는 유형명 부여.  

### Step 2.5 유형별 역량 질문 작성

원래 문항과 정답, 근거를 대조해 유형마다 실제 사용자의 관점과 표현으로 역량 질문을 한 개 이상 작성.  
역량 질문 하나에는 사용자가 알고 싶은 한 가지 내용만 포함하고 클래스명과 열 이름은 제외.  

### Step 2.6 관리자 확인 질문 기록

자료만으로 업무 기준을 확정하기 어렵고 해석에 따라 답이 달라지면  
`{base_dir}/manager_questions.md`에 담당자가 답할 수 있는 질문으로 기록.  
항목마다 확인 번호, 관련 문항 번호(역량 질문 작성 후에는 해당 역량 질문 번호도 포함), 근거 위치, 질문, 담당자 역할과 상태 기록.  
‘추천 답변(초안)’ 칸에는 담당자가 그대로 승인하거나 고쳐 쓸 수 있는 답변 한 문장과 추천 근거를 기록.  
자료로 확인되는 부분과 판단이 필요한 부분을 구분하고, 어느 쪽도 추천할 근거가 없으면 가능한 선택지와 부족한 근거 제시.  
‘관리자 결정’ 칸은 실제 회신 전까지 비워 두고 해당 판단만 보류. 나머지 질문은 계속 검토.  
회신을 받으면 초안을 보존하고 관리자 결정(초안 승인, 수정 답변 또는 보류)과 회신 출처를 기록.  
보류한 항목은 ‘답변 대기’로 유지하고, 확정한 결정을 관련 역량 질문과 설계 범위에 반영한 뒤 ‘반영 완료’로 변경.  

### Step 2.7 설계 범위 설정

여러 역량 질문을 함께 검토해 답에 필요한 정보 묶음 도출. 각 역량 질문에 보완본의 문항 번호와 근거 위치 연결.  
새로운 업무가 발견되면 평가셋 보완 단계에서 먼저 검토한 뒤, 확정된 문항에 한해 역량 질문에 반영.  

### Step 2.8 근거 조회 경로 표시

역량 질문별로 DB 조회, 문서 검색, 문서 간 연결 또는 DB와 문서의 조합 중 필요한 경로 기록.  
여러 원천을 거치는 경우 조회 순서와 연결 단서(같은 대상의 키, 분류 또는 주제) 기록. 세부 스키마 설계는 후속 단계에서 진행.  

### Step 2.9 검토와 승인

가이드 6절에 따라 유형별 역량 질문과 범위 밖 항목 점검. 사용자 검토와 수정을 거쳐 초안 확정.  
실제 응답 가능 여부는 Phase 8에서 별도 표본으로 검증.  

- **산출물** — 설계용 평가셋 보완본(`{eval_dir}/eval-set-design.json`, 확정 문항과 보류 목록 구분),  
  역량 질문표(`competency_questions.md`), 원천 연결 지점 목록(`crossing_points.json`), 관리자 확인 질문 목록(발생 시 `manager_questions.md`).  

## Phase 3 RDB 구조 판정과 읽기 전용 조회 매핑 설계 `[승인]`

### Step 3.1 클래스와 업무 열 확인

- 클래스는 ‘회원’이나 ‘거래’처럼 개별 건을 식별할 수 있는 업무 대상의 유형입니다.  
- 앱에서 거래 내역을 조회할 때 거래번호로 한 건을 찾고, 결제 금액과 거래 일시를 읽습니다.  
  금액과 일시처럼 거래 내용을 설명하는 칸이 ‘업무 열’입니다.  

- 아래 표에서는 한 건을 구별하는 기본 키(PK)나 다른 기록을 가리키는 외래 키(FK)에 속한 열을 제외하고 업무 열을 셉니다.  

### Step 3.2 1차 판정

테이블마다 표를 위에서부터 적용해 클래스 또는 관계 후보와 적용한 규칙을 판정표(`rdb_judgment.md`)에 적습니다.  

| 조건 | 판정 후보 |
|---|---|
| 다른 테이블의 FK가 가리키는 테이블 | 클래스 |
| 나가는 FK가 0개 또는 1개 | 클래스 |
| 나가는 FK가 3개 이상 | 여러 대상을 잇는 클래스(예: 거래나 배정) |
| FK가 2개이고 업무 열이 없음 | 관계 |
| FK가 2개이고 업무 열이 있음 | 클래스 또는 속성이 있는 관계 |

### Step 3.3 역량 질문과 업무 뷰 대조

DB를 사용하는 역량 질문마다 답에 필요한 값과 상세 수준을 적습니다.  
앱에 허용된 뷰의 결과 열, 한 줄이 나타내는 단위, 조회 조건을 보고 필요한 값을 얻을 수 있는지 확인합니다.  
문서도 필요한 역량 질문은 DB에서 읽을 값과 문서에 연결할 키를 확인합니다.  

### Step 3.4 후보 판정

모든 1차 후보를 관련 역량 질문과 뷰에 대조하고, 같은 판정표에 다음 두 결과를 구분해 적습니다.  
① 모델 적합성: 후보가 역량 질문에 필요한 대상과 관계를 표현하는지, 유지하거나 바꾼 이유.  
② 조회 가능성: 근거가 된 뷰와 열, 조회할 수 있는 값과 부족한 정보. 다른 허용 뷰로 보완할 수 있는지도 확인합니다.  
예를 들어 거래 한 건을 묻는데 월별 합계만 조회할 수 있다면 ‘거래 클래스 필요, 개별 거래 조회 불가’로 기록합니다.  
각 판정에 역량 질문 번호를 연결하고, 판단이 갈리는 항목만 담당자에게 확인합니다. 역량 질문에 쓰이지 않는 운영 메타 테이블은 제외 후보로 둡니다.  

### Step 3.5 조회 매핑 작성

판정표를 바탕으로 클래스, 관계, 속성이 어느 테이블과 열에서 나오고 어떤 뷰로 조회되는지  
`rdb_mapping.json`에 기록합니다. 조회에 필요한 키, 조인, 필터, 집계 단위, 기준 시점, 코드표도 함께 적습니다.  
RDB 행은 원본 DB에 그대로 두며 그래프 노드와 관계로 복제하지 않음.  

- RDB 자료형을 XSD 자료형으로 바꾸는 표를 만들고, 표에 없는 자료형은 추측하지 않고 사람에게 물음. PK와 UNIQUE는  
  식별 후보로, FK는 관계 후보로, PK에도 속한 FK 열은 복합 식별자의 일부로 기록함.  

- 이름, 관계 방향, 제외 테이블, 클래스로 볼지 관계로 볼지 모호한 경우는 현업이 확정함.  

### Step 3.6 읽기 전용 조회문 작성

조회 가능한 것으로 판정한 역량 질문마다 매핑에 따라 앱에 허용된 경로로 읽는 SQL을  
`rdb_queries.sql`에 작성합니다. 각 조회문에 해당 역량 질문 번호를 주석으로 표시합니다.  

## Phase 4 문서 추출 단위와 표본 선정 `[승인]`

### Step 4.1 문서 종류와 추출 단위 확인

- 문서 종류와 본문 필드를 확인함. 검색용으로 덧붙인 글 대신 정제된 원문 필드를 사용함.  
- 문서 종류별 최대 30개 청크를 보고, 한 청크에 제목 단위가 여러 개면 조항이나 항목 경계로 나누는 규칙을 제안함.  
  후보 발견, 시험, 실제 인덱싱에서 같은 규칙과 메타데이터 머리줄을 사용함.  

### Step 4.2 표본 묶음 설정

- 문서 종류 안에서 역량 질문에 의미 있는 메타데이터 값으로 묶음을 정함. 없으면 문서 종류 전체를 한 묶음으로 둠.  

### Step 4.3 발견용 표본과 시험용 표본 선정

- 고정 시드로 발견용과 시험용 표본을 겹치지 않게 나눔. 발견용은 묶음별 시작 10건과 상한 30건을 기본으로 하며,  
  시험용은 문서 종류별 30건에서 50건을 기본으로 함. 자료가 적으면 실제 수와 한계를 기록함.  
  시험용에는 답이 없어야 하는 단위도 포함함.  

- 출력파일: `sample_plan.json`, 문서 종류별 `units.json`

### Step 5.1 표본별 후보 추출

## Phase 6 통합 온톨로지와 원천별 초안 설계 `[승인]`

### Step 6.1 온톨로지 표현 방식 설정

- Class와 관계는 OWL, RDFS, SKOS로, 데이터 검사 조건은 SHACL로 Turtle 원본에 기록함. 표준에 없는 낱말만  
  승인한 `{prefix}` 아래에 두고 뜻을 함께 적음.  

### Step 6.2 공통 클래스와 관계 정의

- RDB 판정, 문서 후보, 건너가는 지점을 함께 대조해 공통 Class를 먼저 정함. 같은 이름보다 같은 뜻과 식별 범위를  
  기준으로 합치고, 다른 뜻은 분리함. 역량 질문에 필요한데 후보에 없는 개념은 해당 역량 질문 번호와 함께 추가함.  

- Class에는 한글 이름, 뜻, 해당과 비해당 범위, 동의어, 키를 적음. 관계에는 출발 Class와 도착 Class를 적고,  
  반대 방향의 역량 질문이 있을 때만 역관계를 적음. 값 목록과 상하위 분류는 코드표 근거가 있을 때만 확정함.  

### Step 6.3 원천 간 식별 기준 설정

- 같은 개체를 잇는 규칙을 값 같음, 변환 규칙, 맞추기 표 중 하나로 기록함. 문장과 코드값의 대응이 불분명하면  
  `needs_review`로 남김. 문서 노드에는 RDB의 대상을 가리키는 키만 두고, 이 키로 RDB를 조회함.  

### Step 6.4 문서별 추출 방식과 검사 조건 정의

- 문서 Shape에는 허용 노드 타입, 속성, 관계 패턴, 키 순서와 채우는 방법을 적음. 채우는 방법은 LLM 추출,  
  메타데이터, 맞추기 표 중 하나로 하며, 인덱싱이 만드는 모든 라벨과 관계도 원본에 미리 등록함.  

- 허용 값, 허용 수, 참조 무결성은 SHACL 검사 규칙으로 적음. RDB 조회 결과는 검사할 때만 메모리의  
  온톨로지 개체로 바꾸고 저장하지 않음. 쓰는 Neo4j 버전이 지원하는 제약만 문서 GraphSchema에 넣음.  

### Step 6.5 승인 대상과 생성물 구성

- 승인 대상 원본은 `{prefix}.ttl`, `shapes/rdb.ttl`, 문서 종류별 Shape, `shapes/checks.ttl`, `maps/*.ttl`임.  
  `shapes/rdb.ttl`은 RDB 적재 스키마가 아니라 읽기 전용 조회 결과와 온톨로지의 대응 및 검사 조건임.  

- 초안 폴더에서만 Turtle을 고치고, 문서 GraphSchema와 그림은 Turtle에서 생성함. 생성물은 손으로 고치지 않음.  

### Step 6.6 초안 관리 도구 준비

- 필요한 초안 관리, Turtle 검사, 생성물 작성, 검토표 작성 도구를 `{base_dir}/tools`에 만듦. 각 도구는 경로,  
  문서 종류, 접두어를 입력으로 받고 `--help`와 작은 고정 입력으로 먼저 검증함.  

- 출력파일: 초안 Turtle, 문서별 `schema_draft.json`, Mermaid 그림, `decisions.json`  

## Phase 7 초안과 생성물 검증

### Step 7.1 온톨로지 원본 검사

- Turtle 문법과 meta-SHACL, 값 목록, 키, 채우는 방법, 관계의 양 끝 Class, 건너가는 경로를 검사함.

- RDB 조회가 필요한 역량 질문은 승인된 읽기 전용 SQL로 기대값과 관찰값을 대조함. 문서 조회가 필요한 역량 질문은 초안 GraphSchema를 넣은

- 문서에서 추출한 RDB 키로 원본 DB를 조회해 crossing마다 키 또는 분류가 채워진 비율, 승인 경로로 이어진 건수,

  SHACL 위반도 규칙별로 셈.  

### Step 8.4 대응표 승인과 재시험

- 맞추기 표 후보는 근거와 함께 보여 주고 사람이 승인한 행만 `approved`로 올림. 나머지는 `needs_review` 또는  
  `not_linked`로 남김. 미달이면 설명, 매핑, 규칙 중 고칠 대상을 제안하고 승인 뒤 Phase 6부터 다시 시험함.

  - Turtle, meta-SHACL, 문서 GraphSchema, RDB 매핑, 이름, 제약, UTF-8, 재생성 검사가 실행 로그에서 통과함

  - `approval.json`에 승인자, 승인 일시, 입력 해시, 온톨로지 버전과 지문, 마지막 시험 지표와 추출 절차가 있음  
  - 실제로 수행하지 못한 항목은 `미검증`과 사유로 남아 있으며 완료로 보고되지 않음  

[예시]  
연회비 평가 문항은 이용금액을 묻지만, 정답과 근거인 합성 약관 제10조 제1항에는 연체 여부도 나옵니다.  
그래서 역량 질문을 “다음 해 기본 연회비가 면제되려면 어떤 조건을 모두 충족해야 하나요?”로 잡습니다.  
필요한 정보는 실적을 계산하는 기간, 금액 기준, 연체 여부를 판단하는 시점입니다. 이 역량 질문은 약관에서 답할 수 있습니다.  
회원별 면제 판정까지 업무에 포함된다면, 평가셋을 보완할 때 특정 회원 사례의 약관과 DB의 이용 실적 및 연체 여부를 대조합니다.  
정답과 근거가 확인된 사례를 설계용 보완본에 추가하고, 그 문항에서 “회원별로 면제 조건 충족 여부를 어떻게 판단하나요?”를 도출합니다.  

`Member`와 `BenefitRule`을 Class로 정하고 문서의 상품 키와 RDB 상품 키가 같을 때만 같은 상품으로 이음.  
RDB 거래는 원본 DB에 그대로 두고 합산 결과와 근거가 된 키만 역량 질문의 조회 경로에 연결함. 문서의 업종 표현과 코드표가  
분명히 대응하지 않으면 맞추기 표를 `needs_review`로 남김. 시험에서는 정답 회원과 미충족 회원을 분리해 적중, 오탐,  
실적과 연체 조건의 적용, 문서 근거 위치, 교차 경로 연결을 함께 확인함.
