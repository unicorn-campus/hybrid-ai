# D3 고객 세그먼트별 합성 상담이력

정제·청킹·검색·상담 근거 추출 실습을 위한 합성 원문임.
고객의 불편, 유지 조건, 제안에 대한 수용·거절 이유와 일반 상담을 함께 구성함.
고객·상담사 이름, 연락처, 카드번호, 생일 및 상담 발언은 가상 설정임.
회원ID와 가입일 및 승인 이용금액은 공통 실습 PostgreSQL을 참조함.

## 파일과 규모

| 파일 | 세그먼트 | 고객 | 상담 |
|---|---|---:|---:|
| D3_S01_신규가입_상담이력_합성.txt | 신규 가입 | 2명 | 8건 |
| D3_S02_장기보유_상담이력_합성.txt | 장기 보유 | 2명 | 8건 |
| D3_S03_VIP_상담이력_합성.txt | VIP | 2명 | 8건 |
| D3_S04_휴면직전_상담이력_합성.txt | 휴면 직전 | 2명 | 8건 |
| D3_S05_다중카드_상담이력_합성.txt | 다중 카드 | 2명 | 8건 |
| D3_S06_연회비부담_상담이력_합성.txt | 연회비 부담 | 2명 | 8건 |

총 12명·48건임. 각 고객의 4회 상담을 날짜순으로 묶음.
상담일은 2026년 3~8월이며 가입일 이전 기록은 없음.
회원마다 다른 4회 상담 흐름을 사용함. 한 흐름을 여러 고객에게 반복 배정하지 않음.
기존 날짜별 60파일·2,400건을 대체한 v2 자료를 2026-10-18에 v3로 고침(아래 「v3 변경」).
2026-10-23에 v4로 고침(아래 「v4 변경」).

## v4 변경(2026-10-23)

- 목적: 상담 기록에 한빛 카드 이름이 한 번도 나오지 않아, 상담과 카드 상품 안내를 잇는 그래프 경로를 만들 수 없었음.
  문서 스키마 설계(`verify/doc-schema-prompt-run-v2`)의 역량 질문 X2를 시험할 수 있게 함
- 방법: 상담마다 상담사 마무리 발화 한 줄(「이번 요청에 대해 ‘…’ 내용을 기록하겠습니다」 또는
  「앞선 기록과 연결하고, 이번에는 ‘…’ 내용으로 정리하겠습니다」)에 카드 이름 구만 끼워 넣음(48줄).
  기존 글자는 지우거나 바꾸지 않음. 줄 수, 순서, 청크 경계는 그대로임
- 카드: 실습 PostgreSQL에서 그 회원이 가진 카드 중 상품 ID가 가장 앞선 것. 카드 중복 상담(다중카드 고객 1명, 4건)은
  고객이 같은 역할이라 한 두 장인 한빛 하늘여정과 한빛 자유여행을 함께 넣음
- 고치지 않은 줄: 평가셋(ragas, 인덱서 group2)이 인용하는 줄, 개인정보 줄, DB 집계 줄. 혜택 크기나 자격을 약속하는 말은 넣지 않음
- 함께 고친 파일: `[기록정보]`의 버전 v3 → v4, `_instructor/D3/상담근거_대조표.jsonl`과 `_instructor/D3/생성검증.json`의
  `source_version`(고친 발화는 대조표가 인용하지 않아 인용 글은 그대로임. 발화 768개, 서로 다른 발화 675개도 그대로임)
- 고친 스크립트와 계획: `verify/doc-schema-prompt-run-v2/tools/add_card_names.py`, `output/card_name_plan.json`
- 바꾸기 전 벡터 인덱스, BM25 색인, GraphRAG v0 그래프는 v3 원문 기준임. 다시 인덱싱해야 v4 기준이 됨

## v3 변경(2026-10-18)

- 목적: 상담 근거 추출과 그래프 스키마 후보 실험에서 아래 4가지가 글에 분명히 드러나게 함  
  ① 불만 원인 한 문장 ② 상담사 제안 문장 ③ 제안 수용, 거절 또는 보류와 이유 ④ 보류와 재검토 조건
- 방법: 발화 줄 수와 순서는 그대로 두고, 기록마다 기존 발화 3 ~ 4줄을 같은 역할의 새 발화로 바꿈(전체 164줄).  
  청크 경계, 기록별 발화 16개와 고객-상담사 8쌍, 정제 기대값은 바뀌지 않음
- 고치지 않은 줄: 개인정보가 든 줄, DB 집계 줄, 평가셋(ragas, 인덱서 group2)이 정답 근거로 인용하는 줄
- 고객 성격 유지: 불만형 6명(24건)은 4요소를 넣고 보류 조건은 고객마다 2건 이상. 일반 문의와 반례 고객 6명(24건)은  
  불만을 지어내지 않고 제안과 응답만 넣음(이탈 신호가 없는 반례라는 설계를 지킴)
- 응답 분포: 불만형 수용 6, 거절 12, 보류 6 / 일반형 수용 15, 거절 7, 보류 2
- 상담사 제안은 확약하지 않는 꼴("확인해 안내", "~해 보시겠어요?")만 씀
- 함께 고친 파일: `[기록정보]`의 버전 v2 → v3, `_instructor/D3/상담근거_대조표.jsonl`(바뀐 근거 발화 갱신과 새 필드
  `complaint_cause`, `proposal`, `proposal_decision`, `proposal_reason`, `hold_condition`, `source_version`),
  `_instructor/D3/생성검증.json`(발화 통계 다시 계산, 768개 중 서로 다른 발화 675개, `source_version`)
- 바꾸기 전 벡터 인덱스와 평가 결과 로그는 v2 원문 기준임. 다시 인덱싱하면 v3 기준이 됨

## 상담내용의 구성

- 비용·혜택 불일치·경쟁사 비교 등 이탈과 관련될 수 있는 구체적 고객 진술 포함함.
- 오안내·반복 이관·앱 오류·알림 피로 등 상품 할인만으로 해결하기 어려운 원인 포함함.
- 추가 소비 거부, 채널 선호, 설명·민원 해결 우선 등 제안 시 고려할 조건 포함함.
- 처음 불만이 완화되거나, 제안을 거절하거나, 보류 조건이 달라지는 후속 상담 포함함.
- 일시적인 지출 감소, 한 장만 정리하려는 문의 등 전체 이탈로 단정할 수 없는 반례 포함함.
- 영수증·명세서·정보 확인 등 이탈과 무관한 일반 상담도 포함함.

세그먼트 자체를 이탈 정답으로 취급하지 않음.
해지 문의가 곧 실제 이탈이고, 안내 수용이 곧 유지 성공이라는 뜻은 아님.
추천은 고객이 말한 필요와 제한조건에 근거해 검토할 행동이며 실제 상품 자격·혜택 확약이 아님.

## 사실과 합성 진술의 구분

2026-09-09 사용자 요청에 따라 이 12명은 가입일 이후 2025년 8월~2026년 8월의
월 승인액이 100만원 이상이 되도록 합성 거래가 추가됨. 상담 원문의 집계도 추가 후 금액으로 갱신함.
기존 승인 0건·0원 예시는 더 이상 이 12명에게 적용되지 않음.

상담 중 승인 거래 건수·합계는 해당 상담일 직전월의 DB 집계임. 취소 거래는 제외함.
가입 전 기간은 이용 비교 대상에서 제외함. 이후 거래나 미래 상담을 앞선 상담에 넣지 않음.
고객의 사정과 선호는 합성 진술이며 DB 이용금액 감소의 원인으로 확정하지 않음.
카드 상태·거래·회원 정보를 수정하지 않음.

D1·D2의 시행일은 2027-01-15임. 2026년 상담에서 현재 적용되는 혜택·반환금으로 확약하지 않음.
고객 유지 제안에 실제 상품 조건이 필요하면 시점에 맞는 자료와 자격 확인이 별도로 필요함.

## 정제 실습 6항목

| 대상 | 원문 위치·모양 | 정제 후 기대 |
|---|---|---|
| 고객명 | `[접수정보]`와 일부 고객 발화 | 모든 출현 삭제 |
| 전화·이메일 | 접수정보와 후속 발화, 공백 전화번호 포함 | 전화·이메일 모두 삭제 |
| 카드번호 | 가상 전체 번호·끝 4자리·하이픈 없는 번호 | 전체와 부분 번호 모두 삭제 |
| 회원번호 | `member.member_id`, 예: `M-1042` | 공통 가명화 규칙을 적용하여 메타데이터로 보존 |
| 상담사명 | `[접수정보]` | 일관된 직원 가명ID로 변환 |
| 나이·생년월일 | 숫자 날짜·한글 날짜·정확한 나이 | 생일·정확한 나이를 제거하고 나이대로 모호화 |

원문에는 `source_member_no` 대신 정형 `member_id`를 사용함.
따라서 원문을 대응표로 다시 변환하지 않고 정형과 동일한 가명화 규칙을 적용함.
가상 전화·카드번호의 유효성 검사 실패를 정제 대상 제외 이유로 삼지 않음.
숫자를 전부 삭제하지 않고 회원ID·생일·연락처와 업무 날짜·거래 금액을 구별함.

## 분리·청킹·검색

1. 입력은 `D3_S*.txt` 6개만 선택함. 본 안내문과 `_instructor`는 색인에서 제외함.
2. 줄 시작 `[상담ID]`로 레코드를 분리함. 파일별 8건, 전체 48건을 대조함.
3. `[접수정보]`, `[본인확인]`, `[기록정보]`를 처리하고 필요한 값만 메타데이터로 보존함.
4. `고객:`·`상담사:` 발화 1쌍을 1턴으로 처리함. 기본 4턴·중첩 1턴으로 비교함.
5. 다른 고객·상담 경계를 넘어 중첩하지 않음. 중첩 청크 수를 상담 횟수로 세지 않음.
6. `record_id`, `consult_date`, `channel`, `member_pseudo_id` 및 `turn_range`를 출처 추적에 사용함.

모든 상담은 `doc_type=consult_log`, `access_level=restricted`, `version=v3`임.
`created_at`은 상담일, `owner_dept=customer_service`임.

## 강사용 근거·검증 자료

`_instructor/D3/`에 다음 자료를 제공함. 전부 임베딩 입력에서 제외함.

- `정제검증_기대값.json`: 상담별 삭제 대상·나이대·이전 상담 연결 정보임.
- `회원별_상담목록.json`: 회원별 상담 4건의 ID와 기간임.
- `상담근거_대조표.jsonl`: 고객 진술·구체 설명·제안·반응의 원문 대조용 자료임.
- `이용사실_대조표.json`: 상담시점별 DB 집계 확인용 자료임.
- `생성검증.json`, `독립검증.json`: 건수·중복·회원 연결·정제 대상·턴 경계 검증임.

검색 평가에서는 다음을 확인함.

- 이 고객의 최근 불편은 무엇이고 이전 상담과 무엇이 달라졌는가?
- 어떤 제안을 받아들이거나 거절했으며 고객이 밝힌 이유는 무엇인가?
- 현재 근거로 제안할 행동과 피해야 할 권유는 무엇인가?
- 같은 불편을 말한 다른 고객의 조건을 섞지 않았는가?
- 일반 문의나 일시적 이용 감소를 전체 이탈로 과잉 해석하지 않았는가?
- 권한이 없는 계정에서 제한등급 상담이 차단되는가?

## 예측 학습 범위

사용자 요청에 따라 미래 이탈 정답·확률·위험등급은 생성하지 않음.
현 자료는 상담 특징과 추천 근거를 추출하는 재료임.
예측 모델 학습에는 추후 이탈 정의·관측기간·사후 결과·시점 기준을 정한 정답 데이터가 필요함.
회원ID, 개인정보, 강사용 근거표를 예측 특징으로 사용하지 않음.
학습·검증 분리 시 같은 고객의 여러 상담이 양쪽에 섞이지 않도록 함.
